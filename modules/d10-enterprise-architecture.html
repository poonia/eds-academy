Multi-brand and multi-site

Separate codebases per brand multiply the work, and they drift apart.

Use repoless to run many sites from one codebase, then add a theming layer. Themes are applied as a class on <body> from page metadata, usually set site-wide or per section with bulk metadata.

Choose how to organize CSS. Body-class selectors in shared CSS keep tokens in one place, but every visitor downloads all brands. Adobe considers this best for two or three closely related brands. Separate theme files, loaded in the eager phase from metadata, isolate each brand and suit larger portfolios or white-label sites.

Repoless suits sites that share structure. If a brand differs fundamentally in function, a separate codebase may be justified. AEM authoring can use MSM Live Copies with one Edge Delivery site per locale.

Hybrid with AEM Sites

Few enterprises replace everything at once. A hybrid lets the high-traffic parts move first.

A CDN routes paths to either origin. With the Adobe-managed CDN, an existing AEMaaCS environment can proxy paths to EDS using origin selectors. Akamai and Cloudflare can also combine backends.

Handle what crosses the boundary: header and footer, consent state, analytics continuity, redirects and sitemaps across origins. The aem-embed web component can share EDS content, such as a header, into other sites, with CSS isolated by shadow DOM.

Set an end state. A hybrid with no plan to finish means paying for two platforms indefinitely.

Headless plus EDS

Some content is structured data, or already lives in an app. EDS can work with both.

Keep canonical content in server-rendered HTML wherever possible. JSON2HTML and Bring Your Own Markup can turn structured data into HTML for the delivery pipeline. Content Fragments can reach EDS through an overlay and mapping.

In the other direction, aem-embed lets an existing web app consume AEM content without headless API work, and without releasing the app for each content change. Personalized or transactional data can stay client-side or in an API, loaded after the main content.

Scaling teams

Ten teams pushing into one repository need more structure than one team does.

Create a small platform team that owns shared code, the catalog, configuration and standards. Feature teams contribute through pull requests. Prefer trunk-based work: small merges, short branches, and protection on main. Use CODEOWNERS to require the right reviewers for shared files.

Enablement scales better than gatekeeping: provide templates, documentation, office hours and a clear contribution route. Track a few shared measures, such as Lighthouse results, time to merge and accessibility defects.

Choosing authoring per business unit

Different business units have different needs. One authoring tool does not always suit them all.

Because content source is per site, business units can differ while sharing code. But blocks, and how content is modelled, may differ between document-based authoring and AEM with Universal Editor. Check whether code really can be shared before you promise it.

Adobe recommends Experience Workspace as the default content source for new projects. Decide on evidence: authors’ skills, workflows, compliance, existing systems, and integrations. Check regulation too. For example, aem.live says Experience Workspace HIPAA compliance is “coming soon”, while AEM and SharePoint authoring are compliant.
