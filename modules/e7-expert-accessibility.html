Accessible complex blocks

Tabs, accordions and carousels look simple. Done carelessly, they can make content impossible to reach.

Start with the content. Blocks progressively enhance authored HTML, so everything must make sense as plain sections if scripts fail. Ask if you need the pattern at all. A long list of questions can be plain headings, and carousels often hide content few people reach.

Accordions can use native details and summary, which bring keyboard support and state for free. Tabs need role="tablist", role="tab" and role="tabpanel", linked with aria-controls and aria-labelledby. Use a roving tabindex: only the active tab is in the Tab order, and arrow keys move between tabs.

Carousels need real buttons, a label, and an announcement of the current slide. Avoid auto-advancing. If something moves for more than 5 seconds, WCAG 2.2.2 requires a way to pause, stop or hide it. Hidden slides must be hidden from assistive technology and from the Tab order.

Follow the rule that no ARIA is better than bad ARIA. Then test with a keyboard, a screen reader, 200% zoom and reduced motion. Automated tests will not tell you if the experience works.

Accessible navigation and menus

If a keyboard user cannot get through the header, the rest of the site might as well not exist.

Keep site navigation as links in a nav element with a clear label, and use lists for the structure. A disclosure pattern suits most sites: a real button with aria-expanded opens a group of links. Avoid role="menu", which is meant for application menus and tells screen reader users to expect different keys.

Escape should close an open panel and return focus to its button. On mobile, the toggle needs a name and state, and content behind an open panel should not be reachable. Provide a skip link as the first focusable element, so that keyboard users can go straight to main.

WCAG 2.2 adds that a focused element must not be entirely hidden by sticky content such as a fixed header. Use scroll-padding-top to keep it in view.

Dialogs and focus management

Modals are where focus most often goes wrong: users land behind the dialog, or get stranded when it closes.

Use the native dialog element and showModal(). The browser then makes the rest of the page inert, keeps focus inside, closes on Escape, and renders the backdrop. Give it a name with aria-labelledby. The browser normally returns focus to the element that opened it, but verify this if you create or remove elements.

Decide where focus should go on open: usually the heading or first control. For dynamic changes on a page, use a live region to announce results, such as “12 results found”. Only announce what matters, since constant messages are as unhelpful as silence.

After content is removed, move focus somewhere sensible. If a user deletes a row and focus disappears with it, a keyboard user is sent back to the top of the page.

Motion, contrast, zoom and target size

These are the checks that automated tools catch least often, and that real people notice most.

Motion. Respect prefers-reduced-motion. Parallax and large transitions can cause nausea.

Contrast. Text needs 4.5:1, or 3:1 if large. Controls and focus indicators need 3:1 against what is next to them. Check text placed over images in the worst case, not the average.

Reflow and zoom. Content must work at 320 CSS pixels wide without sideways scrolling, except for parts such as data tables. Text must remain usable at 200%. Do not set heights in pixels on anything containing text.

Target size. WCAG 2.2 AA asks for at least 24 by 24 CSS pixels, with some exceptions such as links inside sentences. Other WCAG 2.2 additions include avoiding drag-only actions, consistent help, and not asking people to re-enter information unnecessarily.

Testing with assistive technology

A scan can say a tab has a name. Only using it can tell you whether the tab makes any sense.

Use a fixed script for each block, so the result does not depend on who is testing. Start with the keyboard alone. Then use a screen reader: VoiceOver with Safari on macOS and iOS, NVDA with Firefox or Chrome on Windows. Listen for each control’s name, role and state, and for what changes when you act on it.

Try the block with real author content: long headings, missing images, one item, and a great many items. Check at 200% zoom, at 320 pixels wide, in Windows forced-colours mode, and with reduced motion. Record what you tested, including the tool and version, because results change over time.

Automated scans remain useful as a floor, particularly in pull requests. They find only a portion of issues, though, so include people with disabilities in testing wherever possible.

Reach every control with Tab. Operate each with the expected keys. Focus is always visible and never trapped.

Hands-on lab: fix an inaccessible tabs block

Goal

Take a mouse-only block to a keyboard-usable one.

You need

A test project, a browser and a screen reader.

Time

About 2 hours

  1. Write or reuse a simple tabs block.
  2. Try it with only a keyboard, and note failures.
  3. Add roles and relationships.
  4. Add a roving tabindex and arrow keys.
  5. Check focus visibility and contrast.
  6. Test at 200% zoom.
  7. Test with a screen reader.
  8. Add a disclosure menu and a native dialog, and run the test script on each.

Expected result

A tabs block usable by keyboard and screen reader.

How to verify

You can reach and activate every tab without a mouse, and each state is announced.

Stretch

Add a deep link that opens a specific tab.

  • Keyboard works
  • Roles correct
  • Focus visible
  • Screen reader tested

Enterprise lens

Build once. One audited tabs block beats five unaudited ones.

Copying ARIA from another site can make things worse. Test what you ship.

Involve people who use assistive technology in your testing where possible.

Native elements such as details add no JavaScript.
