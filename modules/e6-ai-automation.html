AEM MCP servers

AI tools are useful only when they can act on real systems. They are safe only when that access is controlled.

The Model Context Protocol (MCP) lets applications expose tools to language models in a standard way. Adobe offers a unified AEM MCP Server at https://mcp.adobeaemcloud.com/adobe/mcp/aem, with content, Experience Governance, Cloud Manager and Cloud Migration capabilities. Adobe has deprecated its earlier domain-specific servers.

Requests run under the authenticated user’s identity, and follow that user’s AEM permissions. Adobe’s important caution is that, for modifying or deleting content, practitioners should use the AI Assistant interface instead of calling MCP tools directly, because its agents have built-in safeguards.

For Edge Delivery content, Experience Workspace MCP at /adobe/mcp/da has 10 tools, such as da_list_sources, da_get_source, da_create_source and da_delete_source. AEM agentic plugins add features such as request publish and scheduling to the assistant.

AI-assisted development

Coding agents know HTML and JavaScript well, and know nothing about your project until you tell them.

The boilerplate ships with AGENTS.md, covering structure, commands and block conventions. Some tools use their own file name, such as CLAUDE.md. aem.live also publishes llms.txt. Tell your agent to search www.aem.live, or “EDS” can bring back unrelated results, including medical ones.

Skills are reusable workflows that load only when needed. Adobe’s catalog at github.com/adobe/skills includes content-driven-development, page-import, docs-search and block-inventory. Give agents a way to see the page, through screenshots or browser automation.

The same pull request rules apply to AI work. Talk to maintainers before a large change, keep the scope small, run lint, include test URLs, and have a human review it.

Why agents go wrong on EDS

Agents know HTML, CSS and JavaScript well, but they start each session knowing nothing about your project. Without guidance they guess at DOM structure and content models, or skip verification. They also confuse EDS with the Java, JCR and OSGi side of AEM. The fixes are simple: a good AGENTS.md, an instruction to search www.aem.live, mentioning llms.txt, and skills for repeatable work.

Content automation

Automation can publish a thousand pages correctly, or a thousand wrong ones just as quickly.

Good candidates are repetitive, checkable tasks: metadata fixes, link repairs, translations for review, alt text suggestions, and first drafts. Keep a person in charge of what goes live, especially for claims, legal text and anything regulated.

Design automation as stages: select the content, propose a change, validate against rules, review, then publish with a limited credential. Use Experience Workspace versions and snapshots for safe rollback. The Admin API imposes rate limits and has jobs for bulk work, and the audit log records operations.

Verifying what an agent built

A confident explanation is not evidence. The value of an agent depends on how cheaply you can check its work.

Give the agent a way to see results: aem up, a real page, and screenshots or browser automation. Ask it to show evidence rather than claim success. For EDS this means a branch URL, a clean lint, a PageSpeed result, and a screenshot of the block with real content.

Review generated code the same way you review a person’s, with extra attention to the usual gaps. Agents often add dependencies you do not need, use innerHTML on fetched data, replace delivered DOM with client-rendered DOM, write complex selectors, or change unrelated files. Long diffs are hard to check, so keep tasks small.

Check facts as well as code. EDS changes quickly, and an agent may repeat an older approach such as fstab.yaml, helix-query.yaml or a deprecated crontab sheet.

Security for agent pipelines

An agent that reads content and can also publish is a new kind of risk: the content can try to give it orders.

Prompt injection means instructions hidden in material that an agent reads, such as a page, spreadsheet or imported site. Treat everything the agent reads as data. The defence is not a better prompt, but limiting what a tricked agent could do.

Separate the steps. The stage that reads untrusted content should not hold publish rights. Give each credential the fewest roles it needs, and make it short-lived where you can. MCP tools act with the signed-in user’s permissions, so an administrator running an agent gives that agent administrator reach.

Add limits that do not rely on the model: a cap on pages per run, an allowlist of paths, a validation step, and required human approval for anything regulated. Log who ran what, using the audit log, and rehearse how to roll back a bad run.

Hands-on lab: add safe agent context to a project

Goal

Prepare a project and a low-risk automated task.

You need

A test repository and a coding agent you may use.

Time

About 90 minutes

  1. Review your AGENTS.md, or add one.
  2. Add project-specific conventions.
  3. Install Adobe’s Edge Delivery skills if your tool allows it.
  4. Ask for one small block change on a branch.
  5. Verify it in a browser.
  6. Review the diff yourself.
  7. List which content tasks may be automated, and which may not.

Expected result

A project ready for careful agent use.

How to verify

The agent follows your block conventions, and a human reviewed the change.

Stretch

Try read-only Experience Workspace MCP on a test site.

  • Change on a branch
  • Verified in browser
  • Automation limits written
