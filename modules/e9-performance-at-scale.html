Portfolio performance program

One fast site is a project. Fifty fast sites require a program, or standards erode.

Keep an inventory of each site, owner and traffic. Use one set of budgets: Lighthouse 100 on .aem.live as Adobe’s stated expectation, and field results that meet Core Web Vitals for real users. Lab data finds problems before release. Field data shows what visitors experienced.

Prioritize by affected traffic, not by the worst score. Fix common causes centrally. With repoless, one fix to shared code improves every site. Watch third parties, which commonly take over budgets after launch. Keep them late, measured and owned.

Enforce with the tools you have: the pull request PageSpeed check, protected branches, and telemetry reviews. Have a regular review with named owners. Report in business terms, with care: only claim a link between speed and revenue that you have measured.

Budgets and scorecards

Across dozens of sites, nobody can inspect pages one by one. A shared budget and scorecard shows where to look.

A budget states a limit before a problem exists. Set limits for lab scores, field Core Web Vitals, bytes before LCP, and the number of third parties. A scorecard then compares each site with those limits in the same format, so a review takes minutes.

Use the 75th percentile of real visits, the measure Google uses for Core Web Vitals. Include traffic beside each figure, so a minor site’s bad number does not take attention from a major site’s small problem. Show the trend as well as the value.

Combine traffic and severity to rank work. A site’s priority is roughly the number of page views affected, multiplied by how far it misses the target.

Diagnosing a regression

A dip on a chart can be a code change, a new tag, a content change, or simply different traffic. Guessing wastes days.

First, confirm that the change is real. Check the sample size, then look at whether it affects one device type, one page group or everything. Use the OpTel Explorer to split the data by these.

Next, line it up with what changed: code merges, tag releases, content publishes and campaigns. The audit log and Git history give you the timeline. A sudden change usually has one cause. A slow drift is usually accumulating tags or heavier content.

Reproduce it in the lab with PageSpeed Insights on an affected URL. Test a version without the suspected change by using a branch, or by temporarily blocking a request in DevTools. Fix at source, and if the fix is shared code, check another site before merging.

Peak events and reporting value

Executives hear about performance twice: during a big event, and at budget time. Be ready for both.

Before a peak event, aem.live has a dedicated guide to service scaling and high-visibility events. The CDN absorbs page traffic well. Your real risks are elsewhere: third-party scripts, personalized APIs, commerce back ends, and forms. Freeze risky changes, rehearse rollback, know who to contact, and watch telemetry during the event.

When reporting, connect performance to outcomes that you have measured. Compare conversion by speed band, or use a controlled experiment. Avoid applying another company’s published uplift to your revenue. State your sample and method, and report wins and misses together so that the numbers remain credible.

Hands-on lab: build a program one-pager

Goal

Set up a repeatable review for several sites.

You need

Access to telemetry for two or more sites, or sample data.

Time

About 90 minutes

  1. List sites, owners and traffic.
  2. Set budgets.
  3. Collect lab and field numbers.
  4. Rank by traffic affected.
  5. Identify one shared cause.
  6. Propose one guard against regression.
  7. Set a review cadence.
  8. Build a scorecard for three sites, and rank them by affected traffic.

Expected result

A one-page program plan.

How to verify

Each top issue has an owner and a date.

Stretch

Report before and after for one fix.

  • Owners named
  • Budgets set
  • Ranked by traffic
  • Review scheduled
