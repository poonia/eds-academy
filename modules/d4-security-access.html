Site authentication

Intranets and pre-launch sites must be closed, but a badly planned lock can also shut out your own CDN.

Site authentication protects aem.page, aem.live, or both, with site tokens. Create a secret, then list its ID under access/site, access/preview or access/live. If preview or live is set, it overrides site.

Limits matter: it provides authentication only, not authorization. It applies to the whole site, and you cannot customize the denied page. For access rules on particular pages, aem.live documents Closed User Groups, which are enforced by a CDN such as Cloudflare or Akamai.

Once the origin is protected, your CDN must send Authorization: token … on each origin request, or every visitor sees an error. Protection also stops the automatic PageSpeed checks on pull requests, unless Adobe enables a feature flag.

Everyone signed in sees everythingNo authorizationUse CUG or your own controls.

Roles and permissions

Publishing rights are a control. Most audit findings start with “everyone is an admin.”

Roles map under access.admin.role, using exact emails or wildcards such as *@acme.com. Built-in roles are admin, author, publish, develop, config, config_admin and view.

The requireAuth value controls enforcement. auto, the default, enforces sign-in as soon as a role mapping exists. true always enforces it. false does not. A defaultRole applies when no mapping matches.

Grant the smallest role that fits, and check the published permissions table. At the time of writing, that table lists config:write under publish, so a publisher may be able to change configuration.

Content Security Policy

A CSP is the last line of defence when an injection slips through. Done badly, it also blocks your own site.

aem.live recommends script-src 'nonce-aem' 'strict-dynamic'; base-uri 'self'; object-src 'none';. AEM replaces aem with a random value whenever it renders HTML. The value then stays the same while that page is cached. Scripts in your repository’s HTML need nonce="aem".

New boilerplate sites include it in head.html as a meta tag with move-to-http-header="true". The current boilerplate adds more, including 'unsafe-inline' http: https:, a frame-src and require-trusted-types-for 'script'. Compare your copy with the guide, and test before you change it.

For a site already in production, try the meta option in a feature branch, test thoroughly, move it to main, then move to a response header. content-security-policy-report-only offers no protection, and is only for testing.

SymptomCauseFix
Blocks do not loadMissing strict-dynamicAdd it, so trusted scripts can load others.
New static page has blocked scriptsNo nonce markersAdd nonce="aem".
Nonce is literally aemNot configured correctlyRecheck the policy and marker.

Sidekick and IMS sign-in

Which identity system authors use depends on the content source, and that surprises many security reviews.

Sidekick delegates sign-in to the identity provider behind the content source. AEM and Document Authoring use Adobe authentication. Google Drive uses Google, and SharePoint uses Microsoft. A Microsoft tenant admin may first need to grant consent.

Sidekick is a browser extension. Its token sits in session storage, its project configuration in sync storage. It samples anonymous usage data: action names and target URLs, for one in ten interactions. Only trusted Adobe origins can add projects or sign users in on its behalf.

AEM authoringAdobe

access-control-allow-origin: * can expose protected preview and live environments to CSRF attacks against signed-in authors. Limit it to specific origins and URLs.

Secrets handling

Everything in the code repository can reach the browser, so a secret there is effectively public.

EDS has no server-side application tier of your own. Client code cannot hold secrets. Protected API keys go in a CDN worker or backend. For Adobe-managed CDN rules, use Cloud Manager pipeline secret variables, referenced as ${{NAME}}.

Never place secrets in public configuration, block code, sheets or metadata. Treat any leaked credential as compromised, and revoke it first. Then look at audit logs to see what was done with it.

Hands-on lab: harden a test site

Goal

Add authentication, roles and a policy, then prove them.

You need

Admin access to a test site.

Time

About 2 hours

  1. Map an author and a publisher.
  2. Confirm the author cannot publish.
  3. Create a site token and protect preview only.
  4. Check that a request without a token gets 401.
  5. Check that a request with the token works.
  6. Add nonce markers and the CSP in a branch.
  7. Read the browser console for blocked scripts.
  8. Remove the protection, and revoke the token.

Expected result

A verified access model and CSP.

How to verify

The 401, the token request and the blocked-script behaviour all match your plan.

Stretch

Move the CSP to a response header.

  • Role limits tested
  • 401 confirmed
  • CSP tested
  • Token revoked
