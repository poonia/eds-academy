Delivered markup

If you code against what you see in the DOM inspector, you will misread what the server sent. Start with View Source.

Every page has the same shape: a head with title, metadata and head.html, then an empty header, a main with content, and an empty footer.

In main, each top-level div is a section. A block is a div with the block name as its class, containing a div per row and per cell. Default content is plain semantic HTML.

Decoration pipeline

Most block bugs are order bugs. If you know the sequence, you know what exists when your code runs.

decorateMain in scripts.js runs five steps in order: decorateIcons, buildAutoBlocks, decorateSections, decorateBlocks and decorateButtons.

This happens in the eager phase, and the body is hidden until then, which avoids early image downloads and layout shift. After that, the first section is loaded with priority for its first image, the LCP candidate.

Why order matters

Each step depends on the one before. Auto blocks must exist before decorateSections wraps content, or they would be treated as default content. Sections must be wrapped before decorateBlocks looks inside them. Buttons come last so that links inside finished structure are classified correctly.

If you add a step, decide where it belongs in that chain, and keep it synchronous. Anything awaited here delays every page’s LCP.

SymptomCauseFix
Button class is missingLink is not alone in its paragraph, or lacks bold or italicAuthor it as a standalone bold or italic link.

Block loading

Blocks are loaded on demand. Understanding how keeps both the critical path and error handling honest.

loadBlock sets data-block-status to loading, then fetches blocks/name/name.css and dynamically imports name.js in parallel. If the module has a default export, it is called with the block element, and the status becomes loaded.

A failure in one block is caught and logged, so the rest of the page continues. Sections load one by one, and the first section is awaited before lazy loading starts.

Why sections load in order

Sections stay hidden until their blocks are ready, so a visitor never sees a half-built section. Loading one section at a time keeps the order predictable. It also means a slow block delays the sections after it, which is another reason to fetch data without blocking and to reserve space.

Auto-blocking in code

You want every article to have a header block, without asking authors to add it. This is where you implement that.

Add your logic to buildAutoBlocks. Use buildBlock(name, content) to create the markup a block would have had from the server, then insert it into main.

The current boilerplate auto-loads links to /fragments/ and builds widget blocks here. Keep this code tiny, because it runs before LCP, and wrap it in a try/catch as the boilerplate does.

When to reach for it

Auto-blocking suits patterns that authors should not have to build: a hero made from the first image and heading, or an article header from metadata. It keeps documents simple. It is the wrong tool for something authors need to control or move around, because they cannot see or edit a block that exists only in code.

Page crashes on odd contentNo guardCheck elements exist, and keep the try/catch.

From markup to decorated DOM

Your CSS and JavaScript work against the decorated DOM, not the markup in view source. Knowing the differences explains most “why doesn’t my selector match?” problems.

Decoration adds structure and state but does not change the content. Three things are worth remembering.

Sections get the class section, and default content is wrapped in default-content-wrapper. Each block gets a blockname-wrapper parent. A section containing a block also gets blockname-container. Section Metadata becomes data attributes and classes.

Blocks get the class block, plus data-block-name and data-block-status. Sections get data-section-status. These are useful during debugging, since they show exactly how far a page has got.

Buttons are identified by shape. A link alone in a paragraph gets button, and bold or italic around it makes it primary or secondary. Authors never add a class.

A page load, step by step

When a page is slow or flickers, you need to know which step is responsible. This is the sequence to hold in your head.

The browser receives HTML with the body hidden by CSS. scripts.js runs as a module and calls loadEager. That decorates the main element and makes the body visible, then loads the first section and waits for its first image. Fonts may start here on larger screens or if they have already been cached.

loadLazy loads the remaining sections, then the header and footer, lazy-styles.css and fonts. If the URL has a hash, it scrolls to that element once the content is present. The header and footer come after content because they are not on the critical path to LCP, and they have their own publishing life cycle.

loadDelayed runs last. It imports consent-check.js, which declines by default, and loads consented.js only after consent. The boilerplate no longer hard-codes a timer, so if you need the three-second gap that aem.live recommends after LCP, add it yourself.

SymptomCauseFix
Page jumps as header arrivesNo space reservedGive the header a fixed height in styles.css.
Link to #section lands wrongContent was not readyLet loadLazy do the scroll.
Third party starts too earlyNo delay addedAdd a timer in consent-check.js or consented.js.
