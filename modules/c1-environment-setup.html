Boilerplates

A new project should not begin with a blank repository. The boilerplate gives you a loading sequence that is already fast, so your job is not to break it.

Most projects start from adobe/aem-boilerplate, used as a GitHub template. It contains the loading scripts, base styles and starter blocks such as hero, cards, columns, header, footer and fragment. There is no build step: code runs directly from the repository.

Projects that author in AEM with the Universal Editor use a separate template, adobe-rnd/aem-boilerplate-xwalk, which adds component model files. aem.live recommends keeping repositories public, because everything in them is sent to browsers anyway.

What you get on day one

The boilerplate is a working site, not a framework you install. It has no runtime dependency to upgrade, and package.json only lists development tools such as linters. That means the code in the repository is exactly the code a browser receives.

Treat the first day as making three small decisions: which template matches your authoring route, which GitHub organization owns the repository, and which starter blocks you will keep. Delete blocks that you will not use only once you are sure: an unused block costs nothing at runtime, because a block is only requested when a page contains it.

AEM Code Sync GitHub App

Your site has no deployment pipeline to configure. A GitHub App notices each push, and that is what makes the code available.

Install the AEM Code Sync app on your repository. In its repository access settings, choose Only select repositories, select yours and save. From then on, each pushed branch is served automatically, and changes merged to main reach production.

The app also runs Google PageSpeed Insights on pull requests. GitHub Enterprise with IP filtering needs the app’s IP address added to its allow list.

What the app actually does

Code Sync watches GitHub for push events and copies changed files into the Code Bus for that branch. There is no job for you to run, no artifact and no queue to wait for. The usual delay is seconds, and the result is visible at the branch URL.

If a push does not appear, check three things in order: the app is installed on that repository, the repository is in its access list, and the branch name produces a valid host name. Organizations that cannot use GitHub can bring another Git host through Cloud Manager, as covered in D1.

Choose Only select repositories, not All repositories, when you install the app. Grant it only what it needs.

AEM CLI and local preview

Waiting for a push to see a CSS change would ruin your afternoon. The CLI serves your local code with real content.

Install with npm install -g @adobe/aem-cli, then run aem up in your repository. It serves http://localhost:3000, reloads as files change, and fetches content from your site.

Use --url to develop against a specific site, which is essential for repoless projects. --print-index shows the index records for the current page, and --forward-browser-logs sends console output to your terminal.

What local preview really serves

The CLI is a small proxy. A request for a file that exists in your working folder is answered from disk. Everything else, including every page of content, is fetched from the site’s preview host. So you can change code against real content without publishing anything.

Because content is remote, a page must have been previewed at least once to appear locally. Protected sites need a site token, passed with --site-token. Live reload watches your files and is on by default.

Linting and editor

Style arguments waste review time. The boilerplate settles them before you begin.

The boilerplate uses ESLint with the airbnb-base rules and Stylelint. npm run lint runs both, and npm run lint:fix corrects what it can. Its GitHub workflow runs lint on every push.

aem.live advises against changing the rules, even for preference, because that makes it harder to reuse code from the boilerplate and block collection. Install the ESLint and Stylelint editor extensions to see problems as you type.

Branch previews

A reviewer needs to see your block in action. Every branch already has its own URL.

Each branch is served at https://<branch>--<repo>--<owner>.aem.page/ for preview and .aem.live for published content. Content is shared by all branches, so your code runs against real pages.

The combined branch--repo--owner must not exceed 63 characters, and none of the three parts may contain --. Long branch names are the usual cause of a broken URL.

Checking a name before you push

The limit exists because the combined name becomes one DNS label. The hyphens count. A repository called acme-corporate-website in an organization called acme-digital uses 34 characters plus 4 for the separators, which leaves 25 for the branch. Teams with long repository names should agree on short branch prefixes.

The daily development loop

Developers who know each tool can still lose hours to the order they use them in. A steady loop keeps pull requests small and scores green.

A normal change on EDS takes one short branch. Create the branch and run aem up. Choose a real page that shows the problem, and make the change against it. Push early, because the branch URL lets anyone review on a real device.

Open a pull request with a test URL in the description. The bot uses that URL for PageSpeed Insights, and a reviewer uses it to see the result. Merge only when the check is green. After merging, the change is on production code with no deployment step, so verify the same page on the live host.

If a change needs content that does not exist yet, create a draft page, preview it and use that as the test URL. Keep code that depends on new content backward compatible, so that merging before content goes live is safe. D5 covers coordinating the two.

CLI options in practice

Most developers only ever run aem up. A few options solve problems that otherwise look like platform faults.

The options fall into three groups. Server options control where it listens, such as --port when 3000 is taken and --addr to allow other devices. Content options control where pages come from, including --url and --site-token. Debugging options include --print-index, --forward-browser-logs and --log-level.

You can also work without an authoring system. --html-folder serves local HTML files without their extensions, which helps when you draft a page’s markup by hand or with an AI tool. For projects on da.live, aem content clone checks content out to a local content/ folder. aem up then serves matching paths from that folder, and you use status, diff, add, commit and push much as you would with Git.

Hands-on lab: create a site and open a pull request

Goal

Go from an empty GitHub account to a reviewed branch URL.

You need

A GitHub account, Node.js and a code editor.

Time

About 60 minutes

  1. Create a repository from aem-boilerplate.
  2. Install AEM Code Sync on only that repository.
  3. Follow the developer tutorial to connect content.
  4. Run aem up and change a CSS value.
  5. Create a branch and push it.
  6. Open the branch URL.
  7. Open a draft pull request with the URL in its description.

Expected result

A running branch URL and a draft pull request.

How to verify

The branch URL shows your change while main does not.

Stretch

Run aem up --print-index on a page and read the output.

  • Code Sync installed on one repository
  • Local server works
  • Lint passes
  • Branch URL works
  • Draft PR opened

Enterprise lens

Repository settings. Protect main, require reviews, and let administrators bypass only for emergencies.

Never put secrets in the repository. Every file can be served unless it is excluded, and code runs in the browser.
