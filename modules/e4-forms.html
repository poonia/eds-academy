AEM Forms on EDS

Forms are where visitors become customers. Forms that load slowly, or are hard to complete, lose them.

Edge Delivery Services for AEM Forms uses plain HTML, CSS and JavaScript, with no pipeline to wait for. A valid AEM Forms licence is required. There are two authoring methods.

Document-based authoring builds simple forms in Excel or Google Sheets, with rules and validation, attachments, and submission to a spreadsheet or email. WYSIWYG authoring, using Universal Editor, adds the advanced rule editor, client-side extensibility, reCAPTCHA, document of record, Form Data Model and many submission targets.

Adobe’s Forms overview recommends starting new form projects in Universal Editor, unless the team is entirely document-centric and the form is very basic. The Forms Submission Service can save submissions directly to OneDrive, SharePoint or Google Sheets.

Enterprise forms

A loan application is more like a small application than a web page. Its logic, data and audit trail all need design.

The Rule Editor gives authors conditions and actions without code. Patterns include When/Then, Set If and If/Then/Else. It is an extension that must be enabled in Extension Manager. Rules run from top to bottom. Custom functions go in /blocks/form/functions.js, and must be synchronous.

Available submission targets include spreadsheet, email, REST endpoint, SharePoint, OneDrive, Azure Blob Storage, Power Automate, AEM Workflow, Marketo Engage and Adobe Experience Platform. Check the list for your environment: Adobe’s submit action page is not fully consistent, and custom submit actions are listed as early access.

Client-side rules improve the experience. They are not security. Always validate submitted data on the server, protect from spam, minimize the personal data you collect, and agree on retention.

How a form reaches the page

Without a mental model of how a form is built, every form bug looks like a mystery. It is a block, and a small data file.

A form is delivered through the form block. In document-based authoring, a sheet defines the fields and is delivered as JSON at the form’s path. The block fetches that definition, builds HTML form elements, applies rules, and takes care of the submission.

Each row of the sheet is a field. Columns such as Name, Type, Label, Mandatory and Options describe it. In WYSIWYG authoring the definition comes from the Universal Editor instead, but it reaches the browser through the same block.

Because the form block is project code, you own its styling and can add custom field types. Forms are usually lower on a page, so keep them out of the first section where possible. Hide a field with rules rather than with CSS, so that its state is correct on submit.

Accessible and usable forms

A form is usually the point where a visitor becomes a customer, and it is also where accessibility problems stop people altogether.

Every control needs a visible label, tied to it through for and id. A placeholder is not a label. Group related choices in a fieldset with a legend. Ask only for what you need, since each field lowers completion, and collecting less also reduces your privacy risk.

Errors must be specific, placed next to the field, and programmatically linked to it. On submit, move focus to the first error or to a summary. Do not rely on colour alone. Use the right type and autocomplete values, so phones show the right keyboard and browsers can fill details in.

Long forms benefit from being split into steps, as long as progress is clear and earlier answers are kept.

Submission, security and privacy

A form that accepts data carries legal and security duties long after the page looks finished.

Treat everything from the browser as untrusted. Client-side rules are for usability. The system receiving the data must validate type, length, range and business rules again, whatever the page says.

Protect against automated abuse with Google reCAPTCHA in WYSIWYG forms, or a measure such as a honeypot field and rate limiting on your own endpoint. Never put an API key in client code: send data to a proxy or a submit action that holds the credential.

Decide what happens to the data. A spreadsheet is convenient, but it is a poor home for sensitive information, because many people can open it. Agree on who has access and how long data is kept, then state the purpose to the visitor. For regulated records, consider Document of Record and your organization’s approved systems.

Signature interactive: form rules builder

Build a rule, then type in the form to watch it apply. It follows the When/Then and If/Then/Else patterns.

Hands-on lab: design an eligibility form

Goal

Plan a form with conditional logic and a safe submission path.

You need

A Forms-licensed environment if available. Otherwise, do it on paper.

Time

About 2 hours

  1. Write the purpose, and the data you truly need.
  2. Pick an authoring method.
  3. List fields and validation messages.
  4. Write rules as When/Then.
  5. Choose a submission target and owner.
  6. Define server-side validation.
  7. Test keyboard use and error messages.
  8. State how long data is kept.
  9. Link each error to its field, and check it with a screen reader.
  10. Post a request that bypasses the rules, and confirm the receiving system rejects it.

Expected result

A form specification ready to build.

How to verify

Each field has a reason, each rule has a test case, and data has an owner.

Stretch

Build it in the sandbox, and measure completion with telemetry.

  • Data minimized
  • Rules listed
  • Server validation planned
  • Retention agreed

Enterprise lens

Decide the system of record. A spreadsheet is fine for a newsletter, and wrong for a regulated application.

Forms often gather personal data. Involve privacy and legal teams before launch.

Every field needs a real label, and errors must be clear and programmatically linked.

Keep form scripts out of the first load unless the form is the main content.
