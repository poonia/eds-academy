Block contract

Blocks work because the contract is small. Break it and your block simply never loads.

A block named cards lives at blocks/cards/, with cards.js and cards.css. The JavaScript has a default export that receives the block element. It may be async.

All names must match exactly. The folder name comes from the first class on the block’s div, which comes from the authored name, lower-cased with dashes.

What the loader guarantees

By the time your function runs, the block’s CSS has been requested, the block has its classes and status attributes, and its rows and cells are in the DOM. Your job is to reshape what is already there. The function can be async, and the section will wait for it, so do not await anything slow in a first-section block.

Two kinds of failure look alike. If the folder or file name is wrong, the request returns 404. If your code throws, the error is caught and logged. In both cases the page continues, and the block appears undecorated.

Block is not decoratedNamed export onlyUse export default.

Reading content

Authors change content. Code that assumes exact positions breaks the first time they do.

block.children are rows, and each row’s children are cells. Reuse the elements the server delivered, rather than copying their text, so that links, images and emphasis survive.

aem.live notes that replacing a block with a client-rendered DOM is possible but not best practice. Decorate what is there. Be tolerant of empty cells and extra rows.

Config blocks

Some blocks hold settings rather than content. A two-column table reads naturally for authors.

readBlockConfig(block) from aem.js turns name and value rows into an object. Names are converted to class-name form, and values become a link’s href, an image’s src or text, or arrays when there are several.

Common patterns

Tabs, accordions and carousels have been solved. Do not reinvent their accessibility bugs.

Prefer native HTML: details for accordions, real button elements for controls. Use the :scope selector to limit queries to direct children. Use createOptimizedPicture when you re-render images, and do not make every image eager.

Add classes during decoration so that the CSS stays simple. aem.live advises decorating extra classes rather than writing complex selectors.

Async and data blocks

A list of articles needs data. Done poorly, it hurts every visitor; done well, nobody notices.

A block’s decorate can be async. Fetch JSON from the same origin, handle failure, and reserve space to avoid layout shift. Keep data blocks out of the first section where possible.

aem.live reserves client-side rendering for content that is not canonical to the page, such as blocks that list other pages. Observe when the block scrolls near if the data is heavy.

Block Collection reuse

Your project probably needs tabs. Adobe has already published some.

The Block Collection repository includes accordion, cards, carousel, columns, embed, form, fragment, header, footer, hero, modal, quote, search, table, tabs and video. Copy what you need into your project: it becomes your code.

The current boilerplate includes a sync-block-collection.sh script and a workflow to help with this. aem.live’s linting advice exists partly so that this reuse stays easy.

What you are really reusing

aem.live says the primary value of these blocks is their content structure. You will very likely change all of the CSS and JavaScript. There is no promise of backward compatibility and no upgrade path, so a copy is a fork from day one. To be listed, a block must be intuitive to author, have no dependencies, be responsive, inherit its context, avoid hard-coded text, be fast, and be accessible and SEO-friendly. Those seven tests make a good review checklist for your own blocks too.

Read the block’s content model first. Reuse only makes sense if it fits how your authors want to write.

Accessible blocks

A beautiful block that a keyboard cannot use is broken. Fixing it later costs far more.

Keep semantic elements, and add ARIA only where HTML falls short. Make every control keyboard-reachable with visible focus. Announce state changes with aria-expanded and similar attributes.

aem.live suggests using ARIA attributes for styling: if the state is in aria-expanded, your CSS can use it too, and the two cannot drift apart. Every image needs alt text from authoring.

Web components in blocks

A design system may ship web components. They can work on EDS, if you control their cost.

Web components combine custom elements, HTML templates and Shadow DOM. To use one, load its JavaScript and have your block generate the custom element. They can suit design systems shared across teams.

Mind the performance cost, particularly of large libraries, and do not load them before LCP without measuring. Remember that Shadow DOM isolates content from global styles.

Designing a block’s content model

Code can be rewritten in an afternoon. A content model lives in thousands of documents, so a poor one is the most expensive mistake in a block.

aem.live’s advice is to start from the content. Let authors put what they need into a document without any notion of blocks, then introduce sections and blocks only where needed. Leave as much as possible as default content.

Prefer the structure that requires the least explaining. An author should be able to copy a block, paste it and understand it. Infer meaning from what is in a cell, rather than from its position. Avoid columns that only exist to hold settings, and never nest blocks.

Absorb complexity in code. The Columns block works out how many columns an instance has, so authors do not have to say. When a request would add a tenth setting, ask whether the design should instead be two blocks, a variant, or default content.

Widgets versus blocks

Forms, calculators and search results have no authored content. Forcing them into the block library clutters it for authors.

A block adds form and function to content that authors write. A widget is a self-contained piece of application logic that an author adds by pasting a link. Good candidates are forms, search results, filters, dealer locators, account pages and calculators, particularly if they appear in only a few places.

A widget lives in /widgets/name/. It has the same .js and .css as a block, plus its own .html, and often a .json for configuration or data. When a link to the widget’s HTML is alone in its paragraph, it becomes a widget block as the page renders: the HTML is fetched and injected, and the CSS and JavaScript load. The element gets a class named after the widget.

Query parameters on the link become data attributes, so ?name=AEM arrives as widget.dataset.name. That gives authors a simple way to configure a widget without a table.

Link stays a plain linkOther text in the paragraphPut the link alone in its paragraph.

Debugging a block

Most block problems are one of a few causes. A fixed order of checks finds them in minutes.

Start with the delivered markup: open the page with .plain.html added to its path, or view source, and confirm the table became a block with the class you expect. If the class is wrong, the problem is in authoring or naming.

Then check the Network panel for the block’s .js and .css. A 404 means a naming or branch issue. Next, look at data-block-status and the console. A status stuck on loading points at code that never resolves. An error logged here means the block threw.

Last, step through your function with a breakpoint, and look at the decorated DOM. If it works locally and not on the branch URL, the file was probably not pushed, or the case of a file name differs.

SymptomCauseFix
Works locally, 404 on branchFile name case differs, or not pushedMatch case exactly, then push.
Styles missingSelector written against view sourceInspect the decorated DOM.
Block appears twiceDecorated twice in custom codeLet the loader call it.

Enterprise lens

Block governance. Keep a catalogue with owners, content models and test pages.

Block authors set the floor: native elements, keyboard support and focus.

Keep JS small and defer heavy work. First-section blocks are on the path to LCP.

Authored content and fetched JSON can contain unsafe strings. Avoid building HTML from them.
