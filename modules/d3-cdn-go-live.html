Adobe-managed CDN

Your licence includes a CDN. Knowing what it does and does not cover helps you decide whether to use it.

The Adobe-managed CDN is part of the Edge Delivery Services entitlement. You must own the domain and be able to change its DNS. You can bring a certificate, or ask Adobe for one from Let’s Encrypt. HTTPS is required and IPv6 is not supported. Adobe no longer accepts new domains for its bring-your-own-DNS service, so choose this CDN or your own.

You install certificates and domains in Cloud Manager, for both www and the apex. A CDN configuration then maps the domain to your site. Production must use the main branch origin, and push invalidation must be set up in the site configuration.

Advanced rules go in a cdn.yaml file deployed by a configuration pipeline. They can change headers, filter traffic, redirect, select origins and authenticate. Always guard rules with a domain condition.

BYO CDN

Security teams often require control of the WAF, the domain and the certificates. A BYO CDN gives them that, along with the responsibility.

You can use Fastly, Akamai, Cloudflare, CloudFront or the Adobe-managed CDN. Adobe’s guide warns that CloudFront and Cloudflare’s free plan lack the fine-grained purging that busy, large sites need.

Whichever you pick, the origin is https://main--<site>--<org>.aem.live. Adobe sets out mandatory or recommended settings: forward X-Forwarded-Host, send X-Push-Invalidation: enabled, respect origin cache control, compress, forward query parameters and include them in the cache key, and suppress Age or set it to 0.

Push invalidation

Authors expect a publish to show on the real domain quickly. Push invalidation allows long caching and fast updates together.

When content or code changes on an origin with main in its host name, AEM purges the production CDN by URL and by cache tag or key. It takes two steps: the vendor properties in the site’s cdn.prod configuration, and the X-Push-Invalidation: enabled request header.

Other origins do not trigger it by default. A production-like CDN on another branch can set cdn.prod.branch, limited to dev, develop, stg, stage, uat and qa.

SymptomCauseFix
Old page on productionPush invalidation incompleteCheck both configuration and header.
Short cache lifetimeOpt-in header missingSend X-Push-Invalidation.
Staging CDN not purgedNon-main originSet an allowed cdn.prod.branch.

DNS, SSL, apex domains

DNS mistakes are the most visible kind of launch failure, and they can take time to clear.

With the Adobe-managed CDN, point the www CNAME to cdn.adobeaemcloud.com, and the apex A records to the IP addresses Adobe lists. An apex name generally cannot be a CNAME, which is why it needs A records.

The redirect from apex to www depends on the deployment. An Edge environment gets it automatically. With a proxy from AEMaaCS you define the redirect rule yourself.

Every CDN should permanently redirect HTTP to HTTPS, keeping the host, path and query string. It is not on by default everywhere. Lower your DNS TTL ahead of a cutover so that you can reverse it quickly.

RecordNameValue

AapexIP addresses listed on Adobe’s page

Edge redirects

Most redirects belong with authors in a sheet. A few have to run at the edge, and those need care.

The redirects sheet handles exact paths and is reviewed like content. A site can hold up to 100,000. Redirects take precedence over existing pages, and if a workbook has several sheets, only helix-default is used.

Wildcards are not supported in the sheet. Adobe generally advises against them because they accumulate complexity, can cause loops, and tend to send visitors to 404s. Where you do need one, configure it on the CDN.

Go-live checklist

A go-live is a coordinated change across many teams. A checklist keeps the small items from being skipped.

Before launch, finish content, design, accessibility and performance checks on .aem.live. After sign-off, avoid late code or content location changes. Validate analytics, and warn analysts that baselines may move. Add Operational Telemetry to the old site early, for a before-and-after comparison.

You can notify Adobe at aemgolives@adobe.com with the URLs, domain, date and time, primary contact and channel, so that engineering can watch the launch.

After launch, re-check Lighthouse on production, monitor Search Console for weeks, confirm martech tags, and redirect popular 404s.

Hands-on lab: rehearse a cutover on a staging host

Goal

Prove your CDN settings before real traffic arrives.

You need

A test domain and access to a CDN.

Time

About 2 hours

  1. Create a staging hostname that follows your production pattern.
  2. Set the origin to the main aem.live host.
  3. Add the required headers and settings.
  4. Check a page with curl -I.
  5. Configure push invalidation for the staging CDN.
  6. Publish a small change and time it.
  7. Test HTTP to HTTPS, and apex to www.
  8. Write down the steps and how to reverse them.

Expected result

A tested runbook for go-live.

How to verify

A small publish appears on the staging host, and each curl check returns the expected status.

Stretch

Rehearse the rollback too.

  • Origin is main
  • Headers verified
  • Purge timed
  • Rollback written
