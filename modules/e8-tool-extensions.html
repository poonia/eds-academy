Sidekick, DA and UE extensions

Authors often need a tool that does not exist. Knowing the right extension point saves building the wrong thing.

Sidekick takes plugins from a sidekick object in site configuration. A plugin can open a URL, display a popover, or fire a custom event, and is limited by environments and paths. Sidekick also emits events such as sidekick-ready, previewed, published and custom:<name>.

Experience Workspace, also called DA, has an App SDK based on the PostMessage API. A fullscreen app is a first-class tool. A library plugin integrates with the library and document editor. Each is a page and script in your repository, so it follows your normal code lifecycle.

Universal Editor extensions are JavaScript applications built with Adobe App Builder. They can add buttons and actions to the header and properties panel, and can create events. Extension Manager enables them per instance, and Adobe supplies ready-made ones, including Generate Variations and Forms Rule Editor.

Choose the point closest to where the author is working. Prefer a ready-made extension. Then design access, because a tool can act with the signed-in user’s rights.

Building a Sidekick tool end to end

Most useful authoring tools are small pages in your repository. Doing one end to end shows how little is needed.

A palette or popover plugin is simply a page at a path such as /tools/audit.html. With passConfig and passReferrer, it receives the project details and the page being reviewed through query parameters. It can then fetch that page and report on it.

Event plugins run code in the page itself, which suits checks of the rendered DOM. Remember that they do not work in edit or admin views. Because the tool is served from your site, keep it out of the visitor path and add its folder to your CSP thinking. Do not load it for visitors.

Design for authors: state what was checked, what failed and how to fix it. Make it keyboard accessible, and remember that it only sees what the signed-in user can.

Experience Workspace apps

Bulk tasks and content tools can run inside the authoring environment, using the author’s own access.

An app imports the SDK from https://da.live/nx/utils/sdk.js and awaits it to get context (including org and repo), a token and actions. The token authorizes calls to the source API at admin.da.live, so the app can create or change content as that author.

Adobe’s recipes include creating a page by posting HTML as form data, and streaming a list of pages under a path with the crawl utility. crawl takes a callback and a throttle setting, and returns results, the duration and a cancel function. Lower the throttle if your callback performs its own requests.

Add a preview step before bulk changes, offer a cancel button, and show progress. Author Kit and the SDK UI components can help a tool look native.

SymptomCauseFix
App gets no contextOpened outside the editorOpen it through Experience Workspace.
Bulk tool overloads requestsThrottle too highLower it, and offer cancel.

Universal Editor extensions in practice

An extension is a small product with hosting and upgrades of its own, so you should know what you are taking on before starting.

A Universal Editor extension is a JavaScript application, usually built with App Builder. It registers with the editor through Adobe’s UI extensibility model and declares what it adds, such as header buttons or a panel. Once deployed, Extension Manager enables it per instance.

The extension runs in an isolated frame and talks to the editor through a defined interface. Anything that needs a secret belongs in a server-side App Builder action, not the front end.

Plan for ownership. You will need a named team, a pipeline for deployments, monitoring, and a test against each editor update. Check first whether Adobe’s ready-made extensions, a model field, a filter or a Sidekick plugin would do the job.
