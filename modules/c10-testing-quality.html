PR workflow

On EDS, merging is deploying. That makes the pull request your release process.

Avoid pushing directly to main and protect it with branch rules. aem.live recommends small pull requests merged often, in scaled trunk-based development. Include a URL to a page on your branch that shows the change.

Keep the scope to what the title says, and use a draft while work is in flux. Talk to maintainers first, particularly for AI-generated changes. The person who opened a PR is the ideal person to merge it.

Linting standards

Lint is the cheapest reviewer you have.

The boilerplate setup runs ESLint and Stylelint on each change. Do not submit a pull request with lint errors, and do not change the rules for personal preference.

aem.live also advises keeping dependencies current, for example with Renovate, and not reordering CSS properties or re-indenting in a functional PR, to keep the diff focused.

Unit and E2E tests

Not every block needs a test suite, but the code that handles money or logic does.

EDS does not prescribe a test framework. Choose what fits your team. Unit-test pure logic such as parsers and calculations. Use end-to-end tools such as Playwright for critical journeys on branch URLs.

Separate these from load, performance and penetration tests. aem.live’s testing page explains that they answer different questions, and that a raw flood of requests mostly proves that the CDN serves cache.

Accessibility testing

PageSpeed Insights gives you an accessibility score. A perfect one still does not mean a page is accessible.

The PR check covers Accessibility as well as Performance. Automated tools such as Lighthouse and axe catch only part of the problem.

Add manual checks for each block: keyboard only, screen reader, zoom to 200 percent, and reduced motion. Test with authored content, including long text and missing images.

Visual regression

A shared CSS change can break a page you never opened.

Visual regression tools capture screenshots and compare them. EDS gives you the useful part for free: main and your branch both have URLs, so you can compare them directly.

Choose a small set of representative pages per block. Stabilize dynamic data, and avoid noise from animation and dates.

Browser tests on branch URLs

Every branch already has a URL with real content, so end-to-end tests need no test environment.

Point your end-to-end suite at the branch URL. Cover a few journeys that would hurt if they broke: navigation, a key form, and search. Avoid testing every block this way, because browser tests are slow and fragile.

Wait for the state the page actually reports. data-block-status tells you when a block is finished, which is more reliable than a timer. Select elements by role and name rather than by generated structure, since that also exercises accessibility.

Run against stable test pages that authors will not edit, or your tests will fail for reasons that have nothing to do with code.

Load, performance and penetration tests

Teams coming from traditional AEM often plan a load test by habit. On EDS, most such tests measure nothing useful and may get you blocked.

Load testing asks whether the system sustains expected traffic. Performance testing asks whether the experience stays fast. Penetration testing asks whether it can be exploited. They need different tools, targets and interpretation.

aem.live does not require approval for reasonable tests, but it monitors them. A raw HTTP flood proves only that the CDN can serve cached responses. Unless your site is among the most visited in the world, aem.live suggests you can skip a load test. If you run one, test against your production CDN and not the aem.page or aem.live hosts. Use tools that render pages in real browsers, such as WebPageTest or a Playwright harness, and model realistic visits.

Stay near the 99th percentile of your actual traffic. Tests above 200 uncached requests per second from one IP may be rate limited or blocked. Use Operational Telemetry to find the pages that really receive traffic. For extreme scale, coordinate with Adobe first.

Hands-on lab: ship a reviewed change

Goal

Follow the full quality process for one change.

You need

A project with branch protection.

Time

About 90 minutes

  1. Agree the change with a maintainer.
  2. Create a short branch.
  3. Make one focused change.
  4. Run lint.
  5. Test with a keyboard and zoom.
  6. Open a PR with a test URL.
  7. Compare screenshots of main and your branch.
  8. Get approval, then merge it yourself.

Expected result

A merged, reviewed change.

How to verify

The PR has a green check, a test URL and a reviewer’s approval.

Stretch

Add a Playwright smoke test for one journey.

  • Manual accessibility checks
  • Test URL included
