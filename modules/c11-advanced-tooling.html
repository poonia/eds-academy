Sidekick customization

Authors repeatedly need one project-specific action. A plugin puts it on their toolbar.

Customize Sidekick with a sidekick object in site configuration. Plugins have an id, a title, and options such as environments (dev, edit, admin, preview, live, prod, any) and includePaths.

A plugin can open a URL or fire a custom event. Sidekick also emits events such as previewed, published and env-switched, which project code can listen for.

Plugin types, and where they can run

A URL plugin opens a page in a new tab. With isPalette it opens in a floating palette, and with isPopover in a popover. An event plugin fires custom:<name>. Event plugins run your JavaScript in the page, so they only work in the development, preview, live and production environments. They cannot run in the edit or admin views.

Use includePaths and excludePaths to limit a plugin to part of a site. passConfig and passReferrer send the project details to a URL plugin. Because Sidekick may load after your scripts, always check for the element and fall back to sidekick-ready.

Admin API scripting

Publishing 3,000 migrated pages by hand is not a plan.

The Admin API at admin.hlx.page supports status, preview, publish, code, cache, index, config, log and job operations. Authenticate with an API key in X-Auth-Token or Authorization: token. Create keys with only the roles needed.

Rate limits apply: handle 429 responses and back off. Bulk endpoints run as asynchronous jobs, and return a job link to poll.

DA apps and plugins

Authors need a custom tool, with access to protected content.

The Experience Workspace App SDK lets you build fullscreen apps and library plugins. An app is a page and a script on your site, such as /tools/tags.html and /tools/tags/tags.js.

The SDK is based on the postMessage API and lets a tool work with protected content. Import https://da.live/nx/utils/sdk.js as a module.

Edge workers

Some logic must run before the page, for all traffic, without slowing the origin.

If you bring your own CDN, its edge workers can handle live-traffic integrations such as protected APIs. Cloudflare is one documented option for connecting a CDN to EDS, and aem.live’s integration guide lists edge workers for live traffic and author-side tasks.

Keep them small and independent of slow backends, and cache carefully: varying a response by user reduces the cache hit rate. Personal data must not end up in shared cache.

What belongs at the edge

Good fits are small decisions made on every request: routing, header changes, redirects too numerous for the sheet, and proxies that hide a key. Poor fits are anything slow, anything that needs a large dependency, and anything that adds per-visitor variation to otherwise cacheable pages. C9 has a worked proxy.

Shared code across sites

Copies of a codebase drift apart. Repoless removes the copies.

Repoless runs many sites from one codebase. All but the first site need no repository. Profiles group reusable configuration, such as headers, indexes and additional metadata, for several sites in an organization.

For local work, use aem up --url to choose a site. For publish events, aem.live has a webhook and audit log; its GitHub Actions publication events carry a deprecation notice. Be careful: a code merge reaches every site at once.

Admin API job patterns

Publishing one page by script is easy. Publishing 5,000 reliably needs jobs, back-off and a record of what failed.

Single-resource calls answer directly. Bulk calls with a list of paths start an asynchronous job and return 202, with a link to check it. Poll that link at a modest interval until the job has stopped, then read its details for per-path results.

Respect limits. A 429 means slow down, and any retry-after header says how long. Preview operations can return a 503 with an x-error header when the content source is throttling. Do not retry straight away.

Make scripts safe to re-run. Keep a list of the paths that succeeded, send work in batches, and print a summary of failures for a person to review. Use a dedicated API key with only the role it needs, kept in a secret store.

SymptomCauseFix
Script reports success, pages missingStopped at the 202Poll, then read the details.
Repeated 429sImmediate retriesBack off and honour retry-after.
Re-run repeats everythingNo record of progressSave successes, and re-run failures.

Webhooks and change feeds

Search indexes, caches and notifications all need to know when content changes. Polling for that is wasteful, and misses things.

A webhook is called whenever content on a site is previewed or published, at most once a minute. It carries a token, not the changes. Your service passes that token to the Admin API log endpoint, and pages through all the unseen changes.

Acknowledge the webhook immediately and do the work afterward, so a slow job does not cause timeouts. Protect the endpoint using a site secret. Use an API key that can only read logs. Because an event may cover many changes, write your handler to process a batch, and make it safe if the same change appears twice.

The audit log can answer questions after the fact, such as who published what. The older GitHub Actions publication events carry a deprecation notice, so prefer webhooks for new work.

Hands-on lab: script a safe bulk preview

Goal

Preview a list of pages with a key that has limited roles.

You need

A test site and an admin who can create a key.

Time

About 75 minutes

  1. Create an API key with only the roles you need.
  2. Store it in an environment variable.
  3. Check status for one page.
  4. Preview one page and read the response.
  5. Script a list with a pause between calls.
  6. Handle 429 and other errors.
  7. Rotate or delete the key.

Expected result

A safe script with error handling.

How to verify

Each page in your list shows a new preview timestamp.
