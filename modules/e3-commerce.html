Commerce storefront on EDS

Slow stores lose sales. A storefront on EDS keeps the fast page model, and adds ready-made shopping features.

A Commerce Storefront brings together page content, storefront code and Commerce data. Edge Delivery Services delivers content and code to the browser. Commerce blocks then render drop-ins, which request Commerce data.

A drop-in is a ready-made npm package with the whole interface and logic for one shopper job. B2C drop-ins include cart, checkout, order, payment services, personalization, product details, product discovery, recommendations, user account and user authentication. B2B drop-ins cover company, quote, purchase order and requisition work. You connect and customize them through containers, slots and events, rather than building from nothing.

Authors manage pages in Document Authoring, placing commerce blocks in tables. For new storefronts, Adobe’s storefront guide marks Universal Editor as deprecated and directs you to Experience Workspace. Drop-ins have their own licensing terms, so review those for your project.

What a drop-in is made of

A drop-in exposes containers, which are pre-built pieces of interface such as a cart summary. Each container has props for configuration and slots for your own content. An initializer sets the drop-in up with endpoints, language and options. It also publishes events. The boilerplate ships with all the B2C drop-ins pre-installed, so you wire them up rather than building them.

On top of the list above, a Wishlist drop-in lets guests and registered customers save products for later.

Commerce architecture

A store touches catalog, cart, checkout, search, payments and CDN. Knowing which request goes where makes problems traceable.

Storefront requests have two purposes. Catalog requests get product details, prices, search results and recommendations. Shopping operations read or update carts, complete checkout, and manage customer accounts and orders. The starter code has separate API clients for these.

Adobe Commerce as a Cloud Service supports both. With Adobe Commerce Optimizer, the storefront uses its catalog and product discovery services, while an existing commerce platform handles shopping operations.

Commerce data is rendered client-side by default, and Adobe’s SEO guide is direct about this choice: server-side rendering is not a ranking signal, and Google does not crawl every page. AEM Commerce Prerender is an App Builder application that generates product and category HTML on a schedule, then publishes it as an overlay. Render the pages that have crawl demand. Do not assume every SKU needs a page.

Follow a request when something is wrong

Most storefront faults fall on one side of the split. A wrong price or missing product points at catalog configuration and data feeds. An empty cart or failed order points at shopping operations, sessions or store view settings. Open the Network panel, find the GraphQL request, and check which endpoint and headers it used before changing code.

Treat prices and availability as live data. Do not copy them into page content, and do not cache anything that varies by customer in shared HTML.

Connecting a drop-in in a block

Every commerce block follows the same short pattern. Once you recognize it, each drop-in’s documentation is easy to apply.

A commerce block is an ordinary block. It has three jobs. Importing the initializer makes sure that the drop-in is configured. Importing the container and the drop-in’s render function brings in the interface. Calling provider.render(Container, props)(element) puts it on the page.

A page often holds several containers from one drop-in, each mounted in its own element. Because drop-ins are loaded by your block, the usual EDS rules apply: they load with the block, and heavy ones should stay out of the first section where you can manage that.

Configuration such as endpoints and store headers belongs in project configuration, not hard-coded in a block, so that it can vary by environment and store view.

Customizing with slots and design tokens

Forking a drop-in for a small change means owning every future upgrade yourself. The supported extension points cover most needs.

Work up the ladder, and stop as soon as the need is met. Design tokens and CSS handle branding. Props change configured behaviour. Slots add, replace or remove pieces of interface. Events let you react to state. Only when those fail should you extend a drop-in or build a new block.

A slot receives a context object. It has prependSibling, prependChild, replaceWith, appendChild, appendSibling and remove, as well as getSlotElement, onChange and dictionary for the current language.

One rule is easy to break: do not call a context method inside another context method. Create and append a wrapper when the slot mounts, then update the wrapper with normal DOM methods inside onChange.

The event bus and cart continuity

Drop-ins do not call each other. Knowing how they coordinate, and where that stops, explains most state bugs.

Drop-ins and your own blocks share a publish and subscribe system in @dropins/tools/event-bus.js. Subscribe with events.on(), publish with events.emit(), and stop listening with subscription.off(). So a mini cart can update when the cart changes, with no reference to the cart drop-in.

The bus only works within one loaded document. When a shopper goes from the cart to the checkout page, the new page has a new bus. Continuity comes from the server-side cart in Commerce, and from storefront code that rehydrates it. The boilerplate saves the cart ID when cart/data fires, and imports the cart initializer at startup.

An event may already have fired before your block subscribes, particularly on data that loads early. Check the event’s documentation for an option to receive the last value, and for cached readers such as getCartDataFromCache.

Storefront performance and SEO

A store has more moving parts than a marketing site, and each one can quietly take back the speed you started with.

Performance. Product and listing pages depend on data that loads in the browser. Reserve space for prices, images and buttons so nothing shifts. Keep marketing tags and payment scripts away from the path to LCP. Measure by page type, because a home page score tells you nothing about checkout.

SEO. Adobe’s guidance is that server-side rendering is not itself a ranking signal, and that Google does not crawl every page. Use Search Console to find out how much Google crawls. Prerender the products and categories that have crawl demand, and add structured data. AEM Commerce Prerender publishes generated HTML as an overlay, on a schedule.

Going live. Test checkout with real payment settings in a safe environment. Check error handling for payment failures and timeouts. Plan for a surge by finding your commerce back end’s limits, since the CDN will absorb page traffic but API calls still reach your services. Adobe’s 429 troubleshooting is the place to start if those limits are hit.
