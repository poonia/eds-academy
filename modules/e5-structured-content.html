Content Fragments as HTML

A page that only references a fragment shows crawlers and language models nothing useful.

Previously, publishing Content Fragments to EDS embedded only a reference in the HTML. A block then fetched the content with GraphQL. The newer approach publishes each fragment as a self-contained semantic HTML page, with no extra block, query or authored page.

The set-up has three parts. First, in the Configuration Service, add a path mapping and allow-list the fragment model. Second, add an overlay to the content source that points at the json2html service. Third, configure json2html with a path, endpoint, regex, template, and options such as relativeURLPrefix.

When a fragment is published, the Admin API checks the overlay first. The service fetches the fragment as JSON, applies a Mustache template, and the HTML is ingested as a page. You need AEM as a Cloud Service, a site such as one from the xwalk boilerplate, and the Configuration Service.

JSON-driven pages at scale

Ten thousand event or product pages should not be hand-authored. The data already exists.

JSON2HTML is a generic worker that converts JSON into pages through a Mustache template, with no service to deploy. One configuration can map a URL path to an endpoint using {{id}} and a regex. Another can read one large JSON array with arrayKey and pathKey, creating one page per record.

After configuration, you preview a dynamic path to generate it. From then on it behaves like other Edge Delivery content. So plan for scale: bulk preview and publish through jobs, respect rate limits, and decide how updates and deletions in the source reach EDS.

A webhook or scheduled job is a common way to do that synchronization. Be careful with the custom headers in the configuration: API keys belong in a protected configuration, never in a template. Consider the large-site limits, such as 50,000 pages per index and sitemap.

Configuration options to know

headers are sent to the endpoint, and default to a JSON content type. forwardHeaders passes selected incoming headers, for instance so that an admin token can reach AEM. relativeURLPrefix adds a domain to relative src and href values, for the file types BYOM supports. useAEMMapping rewrites links using the site’s path mapping. Without a template, you get a basic default structure.

Writing templates for generated pages

The template decides whether a generated page is a real EDS page, or a page of text that nothing can style.

A Mustache template outputs the same semantic HTML that any EDS page has: a main, a div for each section, default content, and block tables as nested div elements. Metadata goes in a metadata block or in meta tags, so that titles, descriptions and indexing all work.

{{name}} inserts an escaped value. {{{name}}} inserts raw HTML, so use it only for content you trust and that is already clean. {{#list}}...{{/list}} repeats, and also hides a section when the value is empty, which is how you avoid empty blocks. {{^name}}...{{/name}} renders when a value is missing.

Remember that extra elements, spans, data attributes and styles are stripped on ingestion. Block class names may use only letters, digits and single dashes. Images must be reachable by EDS during preview, or the page ends up with broken media.

SymptomCauseFix
Empty block appearsNo section around itWrap it in {{#field}}.
Broken imagesNot reachable during previewUse public URLs or relativeURLPrefix.
Block not recognizedInvalid class nameUse letters, digits and single dashes.

Keeping generated pages in sync

Generating pages is the easy part. A page that outlives its source record is a compliance problem waiting to be found.

Decide how each kind of change in the source reaches EDS. Created records need a preview and a publish. Changed records need the same, ideally only when something really changed, using a hash or a modified date. Deleted records need an unpublish, and perhaps a redirect. That last case is the one teams forget.

Trigger updates from the source where you can, using its webhooks, or run a scheduled job that compares records against what is published. Send work in bulk Admin API jobs, and back off when throttled. Keep a list of failures to retry, and alert someone when a run fails.

Set expectations on freshness with the business. Nightly is fine for a branch directory, but not for a rate that must be accurate within minutes. If data must be current to the second, render that part in the browser.

SymptomCauseFix
Withdrawn items still liveNo deletion handlingCompare runs, then unpublish.
Job hits rate limitsEverything republished nightlyPublish only what changed.
Silent failuresNo alertsRecord outcomes and alert.
