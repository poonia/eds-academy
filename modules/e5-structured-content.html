Content Fragments as HTML

A page that only references a fragment shows crawlers and language models nothing useful.

Previously, publishing Content Fragments to EDS embedded only a reference in the HTML. A block then fetched the content with GraphQL. The newer approach publishes each fragment as a self-contained semantic HTML page, with no extra block, query or authored page.

The set-up has three parts. First, in the Configuration Service, add a path mapping and allow-list the fragment model. Second, add an overlay to the content source that points at the json2html service. Third, configure json2html with a path, endpoint, regex, template, and options such as relativeURLPrefix.

When a fragment is published, the Admin API checks the overlay first. The service fetches the fragment as JSON, applies a Mustache template, and the HTML is ingested as a page. You need AEM as a Cloud Service, a site such as one from the xwalk boilerplate, and the Configuration Service.

JSON-driven pages at scale

Ten thousand event or product pages should not be hand-authored. The data already exists.

JSON2HTML is a generic worker that converts JSON into pages through a Mustache template, with no service to deploy. One configuration can map a URL path to an endpoint using {{id}} and a regex. Another can read one large JSON array with arrayKey and pathKey, creating one page per record.

After configuration, you preview a dynamic path to generate it. From then on it behaves like other Edge Delivery content. So plan for scale: bulk preview and publish through jobs, respect rate limits, and decide how updates and deletions in the source reach EDS.

A webhook or scheduled job is a common way to do that synchronization. Be careful with the custom headers in the configuration: API keys belong in a protected configuration, never in a template. Consider the large-site limits, such as 50,000 pages per index and sitemap.

Hands-on lab: turn a data feed into pages

Goal

Generate pages from JSON, and plan the synchronization.

You need

A test site with Configuration Service access, and a small JSON file you own.

Time

About 2 hours

  1. Create a JSON file with three records.
  2. Write a Mustache template in your repository.
  3. Add the overlay to site content configuration.
  4. Configure json2html for one path.
  5. Preview one dynamic path.
  6. Check the page source for full content.
  7. Write how updates and deletions will sync.

Expected result

A generated page and a sync plan.

How to verify

The page source has the content without running JavaScript.

Stretch

Bulk preview all three through a job.

  • Template stored in repo
  • Overlay configured
  • HTML verified
  • Delete flow planned
