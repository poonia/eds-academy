Audiences and campaigns

A visitor from a paid campaign or on a slow connection may need something different. The plugin handles many of those cases with metadata.

Developers define audiences in project code, as named functions that return a boolean, such as mobile or eu. Authors then add rows such as Audience: Mobile to page metadata, with the URL of that audience’s page. An external service can resolve an audience too, but it blocks rendering until it responds.

Campaigns work in the same way: Campaign: Xmas names a page, and visitors get it through ?campaign=xmas or ?utm_campaign=xmas. A campaign can be limited to audiences.

The plugin also includes consent support for privacy rules. Its availability is limited in the same way as experiments, so check first. Keep audience data out of URLs and shared caches, and avoid very small audiences that could identify someone.

Adobe Target and edge personalization

Target is powerful, and its page changes arrive after the page exists. You must plan for that cost.

Adobe supports two Target integrations. The Web SDK approach, also called alloy, is the recommended, future-proof route. Legacy at.js is also supported. Target’s Visual Experience Composer returns a list of modifications, which apply to the final markup, after blocks are decorated.

The call happens in the eager phase, and affects LCP. In Adobe’s tests on mobile, the first call added about 1.3 s of LCP, and later calls about 0.1 s. Desktop added 0.5 s, then 0.3 to 0.5 s. Enable it only where needed, for example with a Target: on metadata flag.

Complex snippets can cause flicker. Blocks that react to Target’s changes need a MutationObserver. Adobe’s sample calls sendEvent with renderDecisions: false, then applies propositions as blocks finish decorating.

Personalization at the CDN edge can choose content before the HTML arrives, but it must vary the cache carefully and keep personal data out of shared responses.

Target with the Web SDK, step by step

Dropping Target in through a tag manager either slows the first paint or causes flicker. Adobe’s integration works with the loading sequence instead.

Adobe’s approach has four parts. It prepares a small alloy queue and loads the library from your own repository. It calls sendEvent with renderDecisions: false, so that it gets the decisions without applying them. It watches for blocks and sections to reach the loaded status, and applies the matching propositions at that point. Finally, it reports what was shown, in a timeout to avoid a long task.

Feature-flag all of this. A Target: on metadata value means pages with no activity skip the library and the round trip altogether.

Target’s changes land after your block has been decorated. If a block needs to react to them, for example by recalculating a carousel, use a MutationObserver. Selectors written in the Visual Experience Composer depend on the final DOM, so changing a block’s structure can silently break an activity.

Choosing a personalization route

Personalization is often requested as a tool, when what is needed is one specific change for one group. The simplest route that does the job usually wins.

Start by asking what is different, for whom, and how you will know whether it worked. Then go through the options from cheapest to most expensive.

Campaign link: a URL parameter selects a page. It costs no extra requests and suits email and paid traffic. Audience: a browser-side check selects a variant, and suits device type or returning visitors. Target: server-side rules for richer segments and an existing Adobe investment, at a cost in LCP. Edge personalization: the CDN selects content before HTML arrives, which avoids flicker. It needs careful cache variation and engineering effort.

Each extra variant of a page reduces cache efficiency, so vary by small, coarse groups. Never put personal data in a shared response, and do not create audiences so small that they identify someone.
