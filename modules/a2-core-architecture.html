Content sources

Business units at the same company often want different authoring tools: marketing likes documents, compliance wants governed forms in AEM. Knowing the supported sources lets you offer each team a fit without building a second platform.

EDS is decoupled from where content is written. aem.live lists these content sources: AEM authoring with the Universal Editor (and Document Authoring), Microsoft SharePoint (Word and Excel), Google Drive (Docs and Sheets), and bring-your-own-markup (BYOM), where your own service supplies HTML. AEM Content Fragments can also be published to EDS.

Whatever the source, EDS normalizes content during preview, so the same blocks and code render it. Markdown files in GitHub are no longer supported as a content source.

Content Bus, Code Bus, Media Bus

When a page shows old text, a stale image or the wrong CSS, you need to know which storage holds what. The buses are where you look first when debugging.

aem.live describes a storage layer organized into containers it calls buses:

  • Source Bus: documents and spreadsheets in their authored form. Only the API service reads it.
  • Content Bus: previewed and published text, PDFs, SVGs, redirects and similar files, with preview and publish states.
  • Media Bus: images and media in content-addressable storage. Each asset is stored once under a hash with a media_ prefix, so it never changes and can be cached permanently.
  • Code Bus: JavaScript, CSS and other code, kept per branch so each branch is its own environment.
  • Config Bus: site and organization configuration, which can inherit from a profile.

An image in a published page points to the Media Bus by its hash. The boilerplate adds width and format parameters for responsive renditions:

SymptomCauseFix
New CSS shows on a branch but not on mainCode Bus is per branchMerge to main; check the main branch URL.
Author replaced an image but the page shows the old onePage not previewed and published againPreview and publish the page so it references the new media hash.

Rendering pipeline

Authors ask why a table in their document became a carousel, and developers ask where their block's HTML comes from. Both answers live in the rendering pipeline.

When an author previews, the API service pulls the document, converts it to a normalized format and stores it in the Content Bus. The architecture page does not name that format, but the Admin API reports the stored resource as a .md path. When a visitor requests the page, edge delivery renders plain semantic HTML: page metadata becomes <meta> tags, each section becomes a <div> inside <main>, and each block table becomes nested <div>s with the block name as a class.

In the browser, the project's scripts take over. They decorate sections, build auto-blocks, then load each block's JavaScript and CSS, which turns the plain rows and cells into the finished component. That split, simple HTML from the edge and enhancement in the browser, is why pages are both crawlable and fast.

Preview vs live, aem.page and aem.live, branch URLs

Reviewers, legal and developers each need a different URL: legal approves on preview, developers test on a branch, the public sees live. Sending the wrong link causes premature approvals or "it works on my branch" confusion.

Every site has two content states. Preview lives on .aem.page and shows what an author last previewed. Live lives on .aem.live and shows what was last published; your production domain serves live content through the CDN.

Every code branch also gets its own host, built as {branch}--{site}--{org}. So the main branch of site bank-web in org acme is main--bank-web--acme.aem.page for preview and main--bank-web--acme.aem.live for live. A feature branch shows new code against the same content.

Admin service and Admin API

Sidekick buttons are fine for one page. For 400 pages after a migration, a nightly status report, or a scripted re-index, you need the API behind those buttons.

The service that previews and publishes content (aem.live's architecture page calls it the API service) is exposed as the Admin API at https://admin.hlx.page. Sidekick and AEM call it for you. Its main endpoint families take an organization, site, branch (ref) and path:

  • /preview/{org}/{site}/{ref}/{path}: GET status, POST to preview, DELETE to remove the preview
  • /live/{org}/{site}/{ref}/{path}: GET status, POST to publish, DELETE to unpublish
  • /status, /code, /cache, /index, /log, /sitemap, /job and /config/{org}.json for configuration

Bulk variants accept /* as the path with a POST body, and run as jobs you can poll.

Send a token in the x-auth-token header. For one-off work, use the token issued when you sign in to the Admin API. For automation, create an API key limited to the roles it needs with POST /config/{org}/sites/{site}/apiKeys.json, which needs an admin role. Keys expire, and the value is shown only once, so plan to rotate them. Module C11 covers scripting in depth.

SymptomCauseFix
401 or 403 from the APIMissing or under-privileged credentialsUse a token with the right role for that site (module D4).
Publish shows old textPublished without a fresh previewAlways preview, then publish.
Bulk script hammers the APIOne request per page in a tight loopUse the bulk /* endpoints and poll the job.

Delivery and CDN

Your security and network teams will ask who owns the CDN, DNS and certificates, and what happens if one part fails. The delivery layers answer both.

aem.live describes delivery in layers. At the front is web infrastructure (CDN, DNS and TLS certificates), run either by Adobe or by you. Behind it is the edge delivery layer, which runs as two fully redundant, separate implementations in parallel. Behind that is the storage layer of buses.

You can use the Adobe-managed CDN or bring your own: aem.live lists Akamai, Fastly, Cloudflare and CloudFront, each with a setup guide and push invalidation support. Your CDN forwards requests to the site's .aem.live origin.

Caching model and push invalidation

A rate change on a mortgage page must appear within minutes, yet the site must survive a traffic spike from a TV ad. Caching for a long time and still showing fresh content sounds contradictory until you see push invalidation.

EDS lets the CDN keep pages for a long time and then removes them precisely when they change. Publishing triggers a push invalidation that purges every caching layer for the affected paths. Merging code into main purges the affected code resources. Media is different: because its URL contains a hash of the bytes, it never changes and can be cached permanently.

The result: high cache hit rates (fast, cheap, resilient) with freshness controlled by publishing rather than by short time-to-live settings.

ChangeWhat gets purgedWho triggers it
Publish or unpublish a pageThat page in every caching layerAuthor (Sidekick, AEM, Admin API)
Merge to mainAffected code resourcesDeveloper, through AEM Code Sync
Replace an imageNothing: the new image has a new URLAuthor, then preview and publish the page
Emergency purgeSpecific pathsAdmin API /cache endpoint
SymptomCauseFix
Team sets very short cache TTLs "to be safe"Distrust of invalidationRely on push invalidation; short TTLs lose speed and resilience.
A shared fragment changed but pages using it look oldOnly the fragment was publishedPublish the fragment; check whether dependent pages need republishing in your setup (module B4).

Hands-on lab: trace a page through the architecture

Goal

Observe preview, live, media and status for a real EDS site and map each to a bus.

You need

Browser DevTools and a terminal with curl.

Time

About 45 minutes

  1. Pick a page. Use any page on aem.live, or your own tutorial site if you have built one.
  2. Find its branch URLs. The aem.live site's code is in the adobe/helix-website repository, so its main branch preview host is main--helix-website--adobe.aem.page. Open the same path on .aem.page and .aem.live.
  3. Inspect an image. In DevTools, find an image URL starting with media_. Note the hash and the width and format parameters.
  4. Read the response headers. In the Network panel, select the HTML document and note cache-related headers. Compare with an image request.
  5. Ask the Admin API for status. Run curl -i https://admin.hlx.page/status/adobe/helix-website/main/docs/architecture. Expect 401: this project does not allow anonymous status requests, so you are seeing access control at work. To read the preview and live sections of the JSON, run the same request against a site you can access and send your token in x-auth-token.
  6. Draw it. Sketch the flow from source to browser and label which bus each observation came from.

Checked on 8 November 2026: both main--helix-website--adobe hosts responded, and anonymous status requests returned 401. If a host stops responding, run the lab against your own tutorial site.

Expected result

Matching preview and live pages, a hashed media URL, and a status JSON with preview and live dates.

How to verify

Your sketch shows Content, Media and Code buses meeting at edge delivery, with the CDN in front.

Enterprise lens

Governance. Decide per site which source is authoritative, who may publish, and who may call the Admin API. Log bulk operations.

Treat Admin API tokens like passwords: store them in a secrets manager, scope them by role, rotate them, and never put them in client code.

The rendering pipeline preserves semantic structure; protect it by keeping headings and lists in content rather than generating them in JavaScript.

Long CDN caching plus push invalidation is the performance model. Avoid short TTLs and query-string cache busting on pages.
