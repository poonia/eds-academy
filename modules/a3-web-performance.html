Core Web Vitals: LCP, CLS, INP

A mortgage calculator whose button jumps as you tap it, or whose answer appears half a second late, loses applications. Core Web Vitals put numbers on those frustrations, and Google uses them as a page-experience signal in search.

Core Web Vitals are three user-experience metrics. Largest Contentful Paint (LCP) measures loading: when the biggest image or text block in view appears. Cumulative Layout Shift (CLS) measures visual stability: how much content moves unexpectedly. Interaction to Next Paint (INP) measures responsiveness: how long the page takes to visibly react after a tap, click or key press.

Google rates each one Good, Needs improvement or Poor, and assesses them at the 75th percentile of real page loads. A page passes only when all three are Good.

Lighthouse 100

"Fast enough" drifts. A clear, automated bar stops the slow creep of one more tag and one more font that makes enterprise sites sluggish within a year of launch.

aem.live states that every Edge Delivery Services site can and should achieve a Lighthouse score of 100. The bar is the mobile score, because it is harder to reach than desktop. The boilerplate starts at 100 on both.

The bar is enforced where code changes: the AEM GitHub bot runs Google PageSpeed Insights against your pull request and fails it if the score is below 100, with a small buffer for measurement volatility. Lighthouse is a lab test; keep an eye on real-user Core Web Vitals as well.

Three-phase loading: eager, lazy, delayed

Marketing needs analytics, consent, chat and personalization. Performance needs a tiny critical path. Three-phase loading is how EDS gives both, by deciding when each thing loads.

aem.live divides a page's payload and execution into three phases. Eager contains everything needed to reach LCP: decorating the DOM, the first section and the LCP candidate. Lazy contains everything the project controls and serves mostly from the same origin: later sections, remaining images, header and footer, non-blocking libraries and fonts. Delayed contains everything else, such as third-party tags, consent and analytics, which are not material to the first experience.

aem.live advises that the delayed phase should start at least three seconds after LCP. The current boilerplate has no timer: on 8 November 2026 its loadDelayed() ran straight after the lazy phase and imported consent-check.js. Add a timer yourself if your project needs the minimum.

SymptomCauseFix
LCP worsens after adding a tag in head.htmlThird party in the eager pathMove it to delayed.js.
Analytics misses short visitsDelayed phase starts after some visitors leaveAccept it, or capture only essential events earlier with a tiny, first-party snippet; review with privacy.

Why no framework, no build

Developers will ask why they cannot use React and a bundler like on other projects. The answer shapes hiring, training and code reviews, so it needs to be understood rather than just enforced.

Every kilobyte of JavaScript before LCP competes with the hero image on a mobile connection, and frameworks bring a runtime before your first component even renders. EDS projects use vanilla JavaScript and CSS, loaded as native ES modules, and only for blocks actually on the page: a page without a carousel never downloads carousel code.

No build step means the code you push is the code that runs. Every branch is reviewable seconds after a push, there is no bundler configuration to maintain, and debugging happens on the real files. Frameworks are not banned, but they belong in isolated blocks, loaded lazily or delayed, never on the critical path.

SymptomCauseFix
A dist/ folder appears in the repoBundler introduced out of habitRemove it; ship ES modules directly.
preload or preconnect added to "speed things up"Common advice elsewhereaem.live says these do not help LCP here and consume bandwidth; remove them.

Payload budgets

"Keep it fast" is not reviewable. A number is. A payload budget lets an author, a developer and a reviewer all check the same thing.

aem.live gives a rule of thumb: keep the aggregate payload before LCP below 100 KB. That usually produces an LCP quicker than 1560 ms and a PageSpeed Insights score of 100. It also advises that, before LCP, only a single host should carry network payload; extra hosts mean extra connections that compete for the same bandwidth.

Fonts are a special case: it is largely impossible to load web fonts before LCP, so the boilerplate loads them right after and uses size-matched fallback fonts so text does not shift when they arrive. Preloading fonts is discouraged.

Hands-on lab: audit a page against the EDS performance bar

Goal

Measure one of your current pages, find what breaks the budget, and model a fix.

You need

Chrome DevTools and access to PageSpeed Insights.

Time

About 60 minutes

  1. Run PageSpeed Insights on one of your production pages, mobile view. Record the Performance score, LCP, CLS and INP (field data if shown).
  2. Find the LCP element. In the PSI report or DevTools Performance panel, note which element is LCP and when it painted.
  3. Sum the payload before LCP. Record a Performance trace with mobile throttling. Add up transfer sizes of requests that finished before the LCP marker.
  4. Count hosts and third parties before LCP. Filter the Network panel by domain.
  5. Model it. Recreate the main resources in the phase visualizer and move them until the page is within budget.
  6. Compare. Run PSI on an aem.live page and note the differences.

Expected result

A one-page audit: scores, LCP element, KB before LCP, hosts, and three recommended moves.

How to verify

Your recommendations move every third party out of eager and bring modelled payload under 100 KB.

Stretch

Repeat on a page with a cookie banner and measure its CLS impact.

Enterprise lens

Governance. Make Lighthouse 100 (mobile) and the delayed-phase rule part of your definition of done and of vendor contracts.

Consent managers and analytics in the delayed phase still need privacy review; delaying them must not mean collecting before consent.

Performance is accessibility: slow, shifting pages are hardest for people on older devices or using assistive technology.

Budget per page: under 100 KB before LCP, one host, no third parties before LCP, fonts after LCP.
