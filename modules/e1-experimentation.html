Experimentation plugin

Experiments fail when they are too rare, too slow or too complex to set up. EDS tries to remove those obstacles.

In an experiment, the existing page is the control, and a changed version is a challenger. Both are variants. Authors copy the page into a folder such as /experiments/ccx0076/, edit it, then add two metadata rows to the control: Experiment and Experiment Variants. Then they publish the control and each challenger.

Traffic splits evenly by default. Experiment Split overrides it. For example, 10, 20, 30 gives the control the remaining 40%. A page has one page-level experiment, each section can run one, and fragment-level experiments use a manifest. Keep the same experiment ID across pages for a multi-page test.

Check access first. The plugin’s README says it is available to customers in collaboration with AEM Engineering through co-innovation VIP projects. It installs into plugins/experimentation with git subtree, and it needs a loader script and changes to scripts.js. Variants should be excluded from search with noindex,nofollow.

Why this avoids the usual cost

aem.live names three reasons experimentation programs fail: too little traffic, too slow, and too complex to set up. Here a challenger is just another page authored in the usual tools, so there is no separate login. Because the switch happens as part of page loading on your own origin, it does not add a third-party call before LCP.

In preview, a page with a running experiment shows an overlay that lets you switch between variants. Use it to check every variant before you publish the control. For an experiment across several pages, use the same experiment ID everywhere, and list challenger URLs in the same order on each page.

Measuring results

Stopping a test the moment it looks good is the most common way to learn the wrong thing.

Data comes from Operational Telemetry. By default, the engine treats any click as a conversion. For a more specific goal, the plugin integrates with the RUM conversion plugin through a Conversion Name property. Decide on one primary metric before launching.

Significance asks whether a difference could be luck. Telemetry is sampled, so the sample behind your numbers is what counts: 50,000 estimated views at a weight of 100 are only about 500 samples. That is why a low-traffic test may never settle.

Fix the duration in advance, and include full weekly cycles. Do not stop as soon as a result crosses significance. Also watch guardrails such as LCP and errors. A winning conversion rate with a much slower page is a warning.

Planning sample size and duration

Most experiments fail before they start, because the page could never collect enough data to detect the change being tested.

Before building anything, estimate how many samples you need. A common rule of thumb for 80% power at a 5% significance level is n = 16 × p × (1 − p) ÷ d² per variant. Here p is the current conversion rate, and d is the smallest absolute change that you care about.

For a 4% conversion rate and a target of 4.8%, d is 0.008, which gives about 9,600 per variant. Halving the effect you want to detect needs four times the data. That is why small tweaks on quiet pages cannot be tested. Test bigger changes, combine pages using a multi-page experiment, or accept that the question cannot be answered this way.

If results come from sampled data, the number that counts is the sampled count, not the estimate after weighting. Check what sampling applies to your experiment, then divide the sample you need by your daily sampled views. Round up to full weeks, so weekday and weekend behaviour are both included.

Experiment quality and closing a test

A valid result can still be wasted if variants differ by accident, or if a winner never reaches production.

Before launch, write the hypothesis, the primary metric and the planned end date. Check each variant with the preview overlay or the experiment query parameter. Confirm that challengers carry noindex,nofollow, and that each loads as fast as the control. A heavier challenger tests speed as well as your idea.

During the test, do not edit variants, and avoid other changes to the same page. Watch guardrails such as LCP and errors, and stop only if something is broken.

Afterward, make the decision and record it, including inconclusive results. Copy the winner into the control. Remove the metadata, then unpublish and remove challenger pages, adding a redirect if any were shared. A shared log stops teams from re-running settled questions.

Hypothesis, primary metric, guardrails, sample size and end date.

Create challengers under /experiments/<id>/, marked noindex.

Use the overlay or query parameter to view every variant. Compare their load times.

Publish the control and all challengers. Leave them unchanged.

At the planned end, read the result and the guardrails.

Apply the winner, remove metadata, unpublish challengers and log the outcome.

Hands-on lab: plan a real experiment

Goal

Produce a test plan someone could run.

You need

A page with enough traffic, plus access to the plugin if you will run it.

Time

About 75 minutes

  1. Choose a page and write a hypothesis.
  2. Define one primary metric and two guardrails.
  3. Estimate traffic, and divide by the sampling weight.
  4. Set a duration of full weeks.
  5. Create the challenger in an experiments folder.
  6. Add metadata, and exclude variants from search.
  7. Write the decision rule in advance.
  8. Estimate the sample size, and decide if the test is worth running.
  9. Write an experiment record before you publish.

Expected result

A signed-off experiment plan.

How to verify

Someone else can state what result would change your decision.

Stretch

If you have plugin access, run it and record the result.
