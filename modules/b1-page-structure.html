Default content

A branch manager asks why the new savings page needs a developer. Most of it does not: headings, paragraphs, lists, links and images are ordinary document formatting, and EDS already knows what to do with them.

Default content is what an author would naturally type: headings, body text, lists, images, links and emphasis. Word, Google Docs, Markdown and HTML all share these meanings, so EDS maps them straight to semantic HTML.

aem.live advises keeping as much of a page as possible in default content, because it is the most natural way for authors to work. Each heading also gets an automatic ID: lower case with spaces turned into dashes, so “Our History” can be linked as #our-history.

Sections

Marketing wants the rates table on a tinted band below the intro. Sections are how an author groups content so a part of the page can look or behave differently.

A section groups default content and blocks. Authors add a break with three hyphens (---) on a line of their own; in Google Docs a horizontal line also works.

Everything is always in a section, even with no breaks at all. Most section breaks exist because of a visual change, such as a different background colour.

A blank band appears on the pageTwo section breaks in a row, or one at the endRemove the extra ---.

Blocks

A plain table cannot be a card carousel. Blocks let an author ask for richer behaviour without leaving the document, while developers keep the code in one place.

A block is authored as a table whose merged first row names it. The cells carry content, settings or references, and the block’s code decides how to use them. Which blocks exist depends on what your developers have built; the only block common to every site is Metadata.

Blocks live inside sections, and a section can hold several. aem.live is firm that blocks should never be nested, because it makes pages very hard for authors to work with.

Block variants

The same columns block needs a dark version for one campaign. A variant reuses the block rather than asking developers for a new one.

A variant is written in parentheses after the block name, such as Columns (dark, wide). Each one becomes an extra CSS class on the block, which developers use to change its layout or style.

Variants only do something if the project supports them. Keep a list of the ones your site offers, because an unknown class changes nothing and gives no error.

Section Metadata

Sections get styled through a small table. It is powerful, but each one is another thing an author has to remember and can get wrong.

Section Metadata is a special two-column table placed in the section it describes. A Style row becomes CSS classes on the section, an Id row sets its ID for anchor links, and other rows become data-* attributes.

aem.live recommends avoiding it until it is really needed, because it adds complexity for authors. IDs must also be unique within the page, so authors need to watch for collisions.

Page Metadata block

The page’s search result and social card come from metadata. If authors skip it, EDS has to guess.

The Metadata table has the word Metadata in its first row, then one row per property: name on the left, value on the right. It becomes tags in the page head and never appears in the body. Use one per page, by convention at the bottom.

Common properties are title, description and image. template and theme become body classes in the boilerplate. If you omit a description, EDS uses the first paragraph with ten or more words. To remove a value, keep the name and leave its value empty.

Auto-blocking

Every article needs the same author and date banner. If each author had to build that table, they would forget it. Auto-blocking lets code build it for them.

Auto-blocking turns default content and metadata into blocks, with no table in the document. It runs very early in page decoration, before blocks load, and creates the same structure a block would have had from the server.

It often pairs with the template metadata property. As an author you see a simple document, while the page still gets a structured banner. You need to know it exists so you do not add a block by hand that code already creates.

Folder and URL mapping

A document called “RRSP Guide (2026).docx” is about to become a public URL for years. Knowing the rules avoids an ugly one.

With document-based authoring, the folder path and file name become the URL path, starting from your root folder. A / at the end of a path refers to the index document in that folder.

URLs keep only lower-case letters, numbers and dashes. Every other character is replaced by a single dash, and leading and trailing dashes are removed. The full path should not exceed 900 characters.

Source fileURL

The folder mapping feature, which serves one page for a whole range of URLs, is different. Adobe now lists it as deprecated. aem.live feature-flags it and warns against it for sites with SEO needs, because it creates an effectively infinite URL space that always returns 200.

Hands-on lab: author and inspect a real page

Goal

Author a page using every structural feature and confirm the delivered HTML.

You need

A tutorial site and Sidekick, or the simulator above if you have no site yet.

Time

About 60 minutes

  1. Outline the page on paper: what is default content and what truly needs a block?
  2. Author it with headings, a list, a link and an image with alt text.
  3. Add two section breaks and one block with a variant.
  4. Add a Metadata table with a title, a description and an image.
  5. Preview it, then open View Source and find each section, the block’s classes and your head tags.
  6. Add .plain.html to the preview URL and compare it with the full page.

Expected result

A previewed page whose source shows your sections, block classes and metadata.

How to verify

Each authored feature can be matched to a line in View Source.

Stretch

Remove the description and find which paragraph EDS used instead.

  • Most content is default content
  • Sections are divided on purpose
  • A block and a variant are in use
  • Metadata appears in the head
  • The URL matches the rules

Enterprise lens

Governance. Publish a list of approved blocks and variants, and name who may add new ones.

The first section usually holds the LCP element. Keep it simple and avoid heavy blocks at the top.

Anyone with edit rights can change what gets published. Keep site folders restricted to authors.
