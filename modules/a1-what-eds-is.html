Origins and naming

You will search for help and land on posts about Franklin, URLs ending in hlx.page, and repos with an fstab.yaml file. If you cannot map those to today's names, you will follow outdated instructions or think two products exist where there is one.

Edge Delivery Services is Adobe's publishing and delivery service that turns authored content into fast, semantic HTML at the edge of a CDN. It began as an internal Adobe project called Helix, later nicknamed Franklin. In October 2023 Adobe gave it a product name, AEM Edge Delivery Services, and by 2025 Adobe was calling it simply Edge Delivery Services.

The old names live on in technical places. The Admin API still sits at admin.hlx.page, and the old preview and live domains hlx.page and hlx.live became aem.page and aem.live. Think of it like a bank that rebranded: the sign on the building changed, but some forms still carry the old logo.

EDS vs traditional AEM Sites

Your organization already runs AEM Sites with an author tier, publish tier, Dispatcher and Java components. Leaders will ask what changes with EDS: who builds what, how releases work, and whether existing components carry over. You need a crisp, side-by-side answer.

Traditional AEM renders pages on a publish server from Java and HTL components, caches them in the Dispatcher, and puts a CDN in front. Code ships through Maven builds and Cloud Manager pipelines, which take time.

EDS keeps authoring where you want it (documents, Document Authoring, or AEM with the Universal Editor) but moves delivery to an edge service. Content is stored as clean, semantic HTML and served from a CDN. Code is plain JavaScript and CSS in GitHub, organized into blocks; every branch you push is instantly its own preview environment. There is no publish tier or Dispatcher to tune.

An analogy: traditional AEM is a restaurant that cooks every dish in its own kitchen. EDS is a central kitchen that sends ready, well-packed meals to many small counters near customers.

EDS vs headless

An architect proposes a headless CMS plus a React app for a new product site. You need to explain when EDS gives the same flexibility with better SEO and less code, and when headless really is the better tool.

Headless systems store structured content and deliver JSON through GraphQL or REST. A separate front end, often a JavaScript framework, turns that JSON into pages. That is powerful for apps and multiple channels, but it puts rendering, routing, SEO and performance on your team.

EDS delivers finished, semantic HTML pages that search engines and assistive technology read directly, then adds behaviour with small block scripts. It can still serve data: spreadsheets become JSON endpoints, AEM Content Fragments can be published to EDS as semantic HTML, and the JSON2HTML overlay renders EDS-friendly pages from JSON at any endpoint. In practice many enterprises use both: EDS for the public web, headless APIs for apps.

Fit assessment

Before your organization commits, someone has to say which sites move first. A wrong first pick, such as an authenticated portal full of server logic, can sour the whole programme. A good first pick, such as a campaign microsite, builds momentum.

Assess fit along a few dimensions: how content-led the site is, how much server-side logic or authentication it needs, how important search and speed are, which authoring workflow the team needs, and whether it depends on AEM features that are only partly available on EDS. Strong fits are marketing sites, campaign and product pages, blogs, documentation and commerce storefronts (Adobe's commerce storefront is built on EDS). Weaker fits are app-like, logged-in experiences with heavy server rendering.

Fit is rarely all or nothing. A hybrid, where public pages move to EDS and logged-in areas stay where they are, is common (module D10).

Licensing and product packaging

Budget owners will ask what EDS costs and what you need to buy. Knowing the packaging lets you start learning for free today and frame the right questions for your Adobe account team.

According to aem.live, Edge Delivery Services is part of AEM Sites and requires an AEM Sites licence; your Adobe account team estimates licensing from your sites' needs and traffic. Development access does not need a separate licence: anyone can build a project for free by following the developer tutorial on aem.live.

For enterprise programmes, sites are created and managed with Cloud Manager. Since Cloud Manager 2026.4.0 you can create an Edge Delivery site there and choose document-based authoring or AEM Author-based authoring.

Feature lifecycle: early access vs GA

An enterprise roadmap cannot rest on a feature that might change next month. Knowing where a feature sits in Adobe's lifecycle tells you whether to build on it, pilot it, or wait.

Adobe says Edge Delivery Services follows a feature lifecycle rather than a traditional roadmap: when existing features do not meet a need, Adobe works with customers to build a solution, then productizes what proves useful. aem.live describes an "adoption arc" with seven stages, from Interest (an unmet need, nothing built) through Repeatable and Increasing use (young, may change) to Mainstream (fully productized), and finally Decreasing use, Discouraged and Removed.

In everyday terms, "early access" features sit in the young stages and "generally available" ones are Mainstream. aem.live also keeps a list of deprecations and removals, and a "Map of Interest" of AEM Sites features that are not yet, or only partly, available when you author with the Universal Editor.

Hands-on lab: inspect a live EDS site and write a fit memo

Goal

See EDS output with your own eyes and produce a one-page fit memo for one of your sites.

You need

A desktop browser with DevTools. No accounts or installs.

Time

About 45 minutes

  1. Open a page on aem.live. The official documentation site runs on Edge Delivery Services. Open aem.live/docs.
  2. View the delivered HTML. Use View Source (not the Elements panel). Find <main> and notice plain <div> sections, headings and paragraphs: semantic HTML before any JavaScript runs.
  3. Compare with the decorated DOM. Open DevTools Elements. Blocks now carry extra classes and wrappers added by block scripts. Write down two differences.
  4. Find the content-only view. Add .plain.html to a page path (for example /docs/architecture.plain.html). This returns just the content sections, which is how fragments are loaded.
  5. Measure it. Run PageSpeed Insights on the page, mobile view. Note the Performance score and LCP.
  6. Score your own site. Use the fit scorer for one site you publish today.
  7. Write the memo. One page: site name, verdict, top three reasons, risks to verify, and a suggested pilot scope.

Expected result

Notes on source vs decorated DOM, a PSI result, and a fit memo.

How to verify

Your memo cites at least two scorer reasons and one feature to check against aem.live.

Stretch

Repeat steps 2–5 on one of your current AEM pages and compare.

The boilerplate's fragment block fetches .plain.html, so this view is how fragments load. For a home page use /index.plain.html: /.plain.html returned 404 on aem.live when checked on 8 November 2026.

Enterprise lens

Governance. Record an architecture decision for each site: fit verdict, authoring option, feature dependencies and their lifecycle stage.

Public delivery is the default. Anything that needs authentication or per-user data needs explicit design (module D4) or should stay on its current stack.

Semantic HTML gives you a head start on WCAG 2.2 AA and AODA, but accessibility still depends on authored headings, alt text and accessible blocks.

Adopt Lighthouse 100 on mobile as a non-negotiable bar from day one; it is far easier to keep than to recover.
