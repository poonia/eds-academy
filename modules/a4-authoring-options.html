Document-based authoring

A campaign team needs a landing page live by Friday and has never used a CMS. If they can write it in Word or Google Docs, they can publish it themselves.

With document-based authoring, authors write pages in Google Docs or Microsoft Word (in SharePoint) and data in Google Sheets or Excel. Normal formatting carries meaning: a Heading 1 becomes an <h1>, a bulleted list becomes a list. A horizontal rule (---) starts a new section, and a table whose first row holds a name, such as Cards, becomes a block. A Metadata table at the end sets the title, description and image.

Authors use the AEM Sidekick browser extension to preview and publish. Folders become URL paths. Training takes minutes, which is the main strength; the trade-off is less structure and fewer built-in workflows than a CMS.

Document Authoring (da.live)

Teams like documents but want CMS basics: versions, bulk publishing, translation. Document Authoring was built for exactly that gap, and its evolution into Experience Workspace affects whether an enterprise should build on it.

Document Authoring (DA), at da.live, is a browser-based, document-style editor built specifically for EDS. It combines document simplicity with CMS features such as versions, bulk operations and automated translation, and it stores content in EDS's own document-based repository rather than in Google Drive or SharePoint.

aem.live now presents DA as Experience Workspace: an authoring surface you enable on an existing DA project. It adds a visual canvas with layout mode, real-time collaboration between people and AI, an AI assistant, AEM Assets access, MCP connections to other tools, and CMS operations such as scheduling and workflows. Existing DA content and integrations keep working. Experience Workspace only works with the document-based repository, so teams on AEM Author would have to move content to use it.

Universal Editor with AEM Sites

Your organization already governs content in AEM: approvals, multi-site structures, translation, audits. The Universal Editor keeps that governance while delivery moves to EDS.

The Universal Editor is AEM's WYSIWYG editor: authors see a live preview and edit in place, guided by a properties panel with defined fields. It is structure-first: developers define component models and filters that control which fields exist and which blocks can go where.

Content is stored in AEM as a Cloud Service and managed in the Sites console. When it is published, AEM renders the semantic HTML that EDS ingests and publishes it to Edge Delivery Services. While editing, AEM renders the page but pulls scripts, styles and icons from EDS, so authors see the real site. aem.live says AEM features such as workflows, MSM, translation and launches are available; its feature-lifecycle pages track any that are not yet, or only partly, available on the edge.

aem.live’s Experience Workspace setup page recommends Experience Workspace over the Universal Editor for new projects. Existing Universal Editor projects need not change. Experience Workspace needs the EDS document-based repository, so teams that depend on content in AEM should compare the two carefully.

Content Fragments to EDS

Product details, rates, advisor bios and disclaimers are reused across pages and channels. Typing them into each page invites mistakes; structured fragments keep one source of truth.

Content Fragments are structured content in AEM, defined by a model (fields such as product name, rate, disclaimer). aem.live lists the Content Fragment Editor as an authoring choice designed for headless needs, generating JSON for Edge Delivery Services among other uses. Content Fragments can also be published to EDS as semantic HTML, which makes them crawlable and fast. The HTML you get depends on the path mapping and overlay in your site configuration and on the JSON2HTML rendering behind them, so review the output for each model.

A related capability, JSON2HTML, renders EDS-friendly HTML pages from Content Fragments or any JSON endpoint. Together they let you generate many similar pages, such as product or location pages, from structured data.

SymptomCauseFix
Same disclaimer edited in 40 placesNo structured sourceModel it once as a fragment or placeholder.
Generated pages rank poorlyRendered only in client-side JavaScriptPublish as semantic HTML or use JSON2HTML.

Choosing an option

The wrong authoring choice is expensive to undo: content has to move and authors retrain. A short, criteria-based decision, recorded per site, avoids months of rework.

Choose per site or business unit, not per company. The main criteria are: governance needs (approvals, audit trails), multi-site and translation needs, how structured the content is, the authors' existing tools and skills, support requirements, and whether you already run AEM as a Cloud Service. Code can be shared across sites with different sources, so one business unit's choice does not lock in another's.

Repoless

Your company has a dozen brand and regional sites that look and behave alike. Copying the same repository twelve times means twelve places to fix every bug. Repoless means one.

Repoless lets several sites run from one codebase. The first site, the canonical site, links a GitHub repository through AEM Code Sync. Every other site is created through the configuration service and points to that same code; only the first needs its own repository. Pushes to the repository apply to every site using it.

The configuration service organizes this into an organization (named like the GitHub org), profiles (shared settings such as headers, indexes and metadata), sites (content plus code plus configuration; one profile each) and content sources. Sites can use different content sources while sharing code. Repoless also supports separate stage and production sites, and multi-site management with AEM authoring.

Enterprise lens

Governance. Keep an inventory: site, authoring option, content source, support model, owner, review date.

Document sources inherit your Microsoft 365 or Google sharing settings. Restrict site folders to authors; anyone with edit access can change what gets published.

Whatever the tool, accessible output depends on authors: real headings, alt text, meaningful links. Train authors per option (module B8).

All options deliver through EDS. Performance depends on blocks and images, not on the authoring tool.
