Eager, lazy, delayed in code

A3 taught the idea. Here is where each line of your code actually goes.

loadEager decorates main and awaits the first section. loadLazy loads the header, the remaining sections, the footer, lazy-styles.css and fonts. loadDelayed runs last.

aem.live’s test for the delayed phase is about third parties and anything not material to the experience. It advises starting at least three seconds after LCP. The current boilerplate has no timer, so add one if you need to.

LCP optimization

LCP usually comes down to a few decisions about the first section.

aem.live’s rule of thumb is to keep the total payload before LCP under 100 KB. Avoid connecting to a second origin before LCP, because setting up the connection costs time, particularly on mobile.

Keep the first section small: the fewer blocks it has, the faster LCP can be. Do not load large libraries for first-section blocks.

What is on the path to LCP

Count the requests a browser must complete before the hero appears: HTML, styles.css, aem.js, scripts.js, the hero block’s JavaScript and CSS, and the image. Keeping their combined size below 100 KB usually gives an LCP that scores 100 in PageSpeed Insights. Changing the order of those requests on a constrained mobile network makes little difference: cutting bytes does.

Image handling

A block that re-creates images can quietly undo what the platform did for you.

Use createOptimizedPicture(src, alt, eager, breakpoints) to build responsive pictures. Its default is 2000 px from 600 px up and 750 px below. waitForFirstImage marks the first image eager.

Choose widths for how large a block really displays images. The Cards block in the boilerplate uses [{ width: '750' }]. Pass eager only for the true LCP image.

Third-party governance

Each tag is a small decision that nobody owns, until the site is slow.

Keep an inventory: tag, owner, purpose, cost and review date. Load through the delayed phase and behind consent. aem.live strongly advises against adding martech to head.html.

Budget third parties like any other performance cost. Measure each in the field, and remove tags with no owner.

PR performance gates

Performance decays one small change at a time. A gate on every pull request stops it.

AEM Code Sync runs Google PageSpeed Insights for each change in a pull request. aem.live says not to submit a pull request for review without a green score for mobile and desktop, ideally 100 for both.

Include a test URL with the block, so that the check covers relevant content. aem.live favours PageSpeed Insights as the common measure over custom Lighthouse configurations.

RUM-driven tuning

A lab score says what could happen. Field data says what did.

Operational Telemetry, also known as real use monitoring, collects performance data from a sample of real visits. It uses no cookies or other client-side state, sends data with navigator.sendBeacon, and does not fingerprint visitors.

Field results often differ from lab results because real devices and networks vary. For small changes, variance and low traffic can make results hard to read. The OpTel Explorer tool helps you examine the data.

Lab and field answer different questions

Use the lab to compare two versions of code under the same conditions. Use the field to find out what visitors really experience. A lab score that holds at 100 while field LCP worsens usually means the real pages, devices or traffic are different from the test page. For small changes, wait for enough traffic before drawing a conclusion.

LCP edge cases

The boilerplate guesses the first image is the LCP element. When that is wrong, the page can be slow despite doing everything else right.

The LCP element is not in the markup. If the hero is fetched from a fragment or service, the loader must not pick a candidate until the block has updated the DOM. Make sure the first block finishes that work before waitForFirstImage runs. Better still, put the content in the page.

There are two hero images. When content holds one for desktop and one for mobile, the hero block should remove the one that is not needed before it starts loading. Otherwise a visitor downloads an unused image, or worse, loads the wrong one first.

The LCP is not an image. It can be a long heading, or a video poster. Then focus on getting that text or poster displayed, including the CSS and font it depends on.

The image is in a lazily built structure. If a carousel re-renders its pictures, pass eager for the first slide only.

SymptomCauseFix
LCP image is lazyChosen after the first image rule ranFinish block work first.
Two images downloadedBoth left in the DOMRemove one in the block.
LCP waits on a serviceHero fetched from an APIMove hero content into the page.

INP and the main thread

A page can load instantly and still feel broken if taps take a second to respond. INP measures that.

Interaction to Next Paint measures how long the page takes to respond to interactions across a visit. A good result is 200 milliseconds or less. It is caused by long tasks on the main thread: the browser cannot respond while your JavaScript, or a third party’s, is running.

Keep handlers short. Do what shows the result first, then defer the rest. Split long loops so the browser can paint between pieces. Third-party tags are the most common cause, which is another reason to gate them, remove those without an owner, and consider moving heavy work to a web worker.

Lighthouse cannot measure real interactions, so it reports Total Blocking Time as a proxy. Use Operational Telemetry to see INP from real visits.

SymptomCauseFix
Menu reacts slowlyLong task in a handlerUpdate the UI first, and defer the rest.
INP worsens after a tag is addedThird-party long tasksDelay or remove the tag.
Large list blocks the pageOne long loopYield in chunks.

Hands-on lab: diagnose a slow page

Goal

Take a slow branch to a measured improvement.

You need

A branch, PageSpeed Insights and DevTools.

Time

About 90 minutes

  1. Run PageSpeed Insights on a page and save the result.
  2. Find the LCP element.
  3. List requests before LCP and total their size.
  4. Find any second origin before LCP.
  5. Make one change at a time.
  6. Re-measure and note the result.
  7. Write it up in a pull request.

Expected result

A before and after comparison, with an explanation.

How to verify

The score improves and you can explain why.

Stretch

Check the page in OpTel Explorer after the change has shipped.

  • Measured a baseline
  • Identified the LCP element
  • Totalled the payload
  • Improved something
  • Documented it

Enterprise lens

Budget. Publish performance budgets, and treat a red score as a blocked release.

Do not add personal data to telemetry.

Speed helps people on older devices and slow connections. Respect reduced motion too.

Aim for Lighthouse 100, and treat each regression as a defect.
