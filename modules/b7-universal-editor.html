Editor interface

An AEM-experienced author moves to EDS and wonders what changed. Most of the mental model transfers, but some words differ.

With AEM authoring, the Universal Editor edits content that lives in AEM, on a canvas that shows the real page. The same concepts of sections and blocks apply, and the editor calls blocks components.

Details of a component are set in the Properties panel. aem.live now recommends Experience Workspace for new projects (module B6). Existing Universal Editor projects need not change.

Sites console for EDS

Page creation, moves and organization still happen where AEM authors expect.

The AEM Sites console is used for content management, such as creating pages, Experience Fragments and Content Fragments. A project needs path mapping to relate AEM content paths to public URLs.

Spreadsheets are also authored in AEM, and Sidekick’s preview adds a table view of sheet data, with a Show changes diff since the last publication.

Components and filters

If authors can drop anything anywhere, consistency goes first. Filters decide what can be added where.

Three files define the authoring experience: component-definition.json lists what can be added, component-models.json defines each one’s fields, and component-filters.json controls what each container allows.

In Adobe’s AEM authoring boilerplate, each block keeps a JSON fragment, and a pre-commit step compiles them into those files. Adding a block to a section’s filter list makes it available there.

SymptomCauseFix
New block is not in AddNot in the container’s filterAdd its ID to the filter list.
File changes do not applyFragments were not compiledRun the project’s build step and commit.

Publishing to EDS

Authors must know exactly what each publish choice does to preview and live.

In the Universal Editor, Publish offers two destinations: Preview or Live. From the Sites console, Quick Publish has the same effect as Live, and Manage Publication offers Preview or Live and scheduling.

Edge Delivery runs pre-publish checks. If one fails, the operation stops with an error, though a few checks silently exclude the affected resource. Related AEM Assets publish with the page, using a technical account.

Content Fragments in UE

Product data is already modelled as Content Fragments. EDS pages should use it without retyping it.

Earlier approaches published only a reference to a fragment, which limited what search engines and LLM agents could read. The overlay approach publishes Content Fragments to EDS as self-contained semantic HTML.

You define path mapping and an overlay in site configuration, instead of GraphQL endpoints and queries, and the JSON2HTML service generates the HTML. The result depends on that configuration, so review the output for each model.

Older patternOverlay pattern
Reference on a pageFull content in HTML
GraphQL query per modelMapping in site configuration
Block per modelGenerated page

MSM, language copies, launches

One global site becomes twelve. AEM’s multi-site features carry over, with one extra requirement.

aem.live states that AEM features such as workflows, MSM, translation and Launches are available when you author with AEM. Multi Site Manager keeps Live Copies in sync with their source while allowing local variation.

On EDS, using MSM requires the repoless feature, so that localized sites share central code. A typical structure keeps language masters under /content/website/language-masters/en and so on.

aem.live’s lifecycle pages track any exceptions by feature. Check each MSM, translation or Launch behaviour that you depend on.

SymptomCauseFix
Local edits are overwrittenInheritance was not cancelledFollow your live copy rules for that component.

Workflows and tagging

Regulated content needs approval trails, and AEM already provides them.

AEM workflows remain available for approval and governance when you author with AEM, and scheduling is available in Manage Publication. Define the workflow before go-live, and test that it covers publishing to EDS.

Tags are created in the Tagging Console. Because the Universal Editor works with tag IDs, create a Taxonomy page to expose their descriptions in every language (module B3).

Hands-on lab: edit and publish a page in the Universal Editor

Goal

Author a page, compare publish destinations and control what can be added.

You need

An AEM sandbox with an Edge Delivery site, or a walkthrough.

Time

About 75 minutes

  1. Create a page in the Sites console.
  2. Open it in the Universal Editor and add a section and component.
  3. Set fields in the Properties panel.
  4. Publish to Preview and compare aem.page and aem.live.
  5. Publish to Live and compare again.
  6. Find a filter in the repository and explain what it allows.
  7. Unpublish from Live and check both hosts.

Expected result

A table of what each action did on each host.

How to verify

Your observations match the table in topic 4.

Enterprise lens

Model governance. Review model and filter changes like code, because they change every author’s options.

The technical account publishes on behalf of authors. Keep its permissions limited, and monitor them.

Make alt text and heading level fields required where possible in component models.

AEM authoring does not change EDS delivery. Keep models simple, so that blocks remain lightweight.
