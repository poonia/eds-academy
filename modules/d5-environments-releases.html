Branch-based environments

Traditional projects queue up for shared environments. On EDS, each branch already has its own.

Code changes come straight from your Git branches. There is no CI/CD pipeline as in traditional AEM as a Cloud Service. Within seconds, each branch is available at https://<branch>--<site>--<org>.aem.page and .aem.live.

aem.live says most customers probably do not need a staging environment. Protect main by requiring a pull request, passing status checks and branches that are up to date. A separate staging branch mapped to its own CDN site is not advised.

Remember that aem.page is for content preview, with different caching. Test code on the .aem.live branch host. Adobe recommends small, frequent merges, in the manner of Scaled Trunk-based Development.

Stage and prod with repoless

AEM authoring teams often have separate stage and production authoring programs. Repoless can follow that shape with one codebase.

With AEM authoring, you can create a second site, such as website-prod, in the Configuration Service. It uses the same code, while its content.source.url points at its own delivery path. The site name in the POST URL must match the one in the source URL.

You then add path mappings and update the AEM cloud configuration for that site. A CDN-level staging environment is a separate matter. It is only worth building if you have complex CDN rules or edge code, and should use main--…aem.live as its origin.

Content release coordination

A product launch can change hundreds of pages at one moment, and those pages need review first.

Snapshots capture a set of previewed pages at a point in time, like a branch for content. Reviewers use a .aem.reviews environment to see the whole site as it will be. Requesting review locks the snapshot, rejecting it unlocks it, and approving publishes it.

A copy in a snapshot stays fixed even if the page changes, unless you update it there. Viewing needs aem.page access, editing needs the author role, and publishing needs the publish role.

For a timed launch, Scheduled Publishing can publish a snapshot or individual pages at a set time. Experience Workspace has it built in, through a scheduling app. Other authoring registers the org and site with Adobe’s scheduling service, using an Admin API key that can publish, and can add a Schedule Publish plugin to Sidekick. On AEM authoring, Manage Publication provides scheduling. The older crontab sheet in .helix is listed as deprecated, so avoid it for new work.

Rollback

A rollback that nobody has rehearsed is only a hope.

Roll back the layer that changed. For code, revert the pull request on main, which goes live through Code Sync. For content, restore the earlier source version, then preview and publish it again. Experience Workspace, AEM and common document tools keep versions.

For configuration, re-apply your saved copy. For a new site or a platform change, keep the old origin ready and switch the CDN back. The more you prefer new-site-then-switch over in-place edits, the simpler this is.

Hands-on lab: run a rehearsal release

Goal

Ship a code change and a content change, then undo both.

You need

A test site and permission to merge.

Time

About 90 minutes

  1. Create a branch and change one block in a backward-compatible way.
  2. Open a pull request with a test URL.
  3. Create a snapshot with two pages.
  4. Review it on .aem.reviews.
  5. Merge the code.
  6. Approve the snapshot.
  7. Revert the code with a pull request.
  8. Restore a page, preview and publish.

Expected result

A documented release and rollback.

How to verify

Your branch, reviews, production and restored page show the expected state at each step.

Stretch

Time each rollback.

  • Test URL in PR
  • Snapshot reviewed
  • Code reverted
  • Page restored

Enterprise lens

Change control. Map pull requests and snapshot approvals to your change records, so that audit evidence comes from the tools.

Approving a snapshot publishes it. Make sure that the approver knows that.

Include an accessibility check in every pull request template and snapshot review.

Treat a failed PageSpeed check as a failed release gate.
