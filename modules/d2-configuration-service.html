Site and org config

Headers, access, CDN settings and code location all live in one service. If you know its shape, you can change them safely.

The Configuration Service gathers settings for the client, delivery, the HTML pipeline and the Admin Service. Most changes can be made at tools.aem.live. The service is API first, so it also suits automation through admin.hlx.page.

You can replace a whole site document or change one part, such as code, content, access, cdn, headers, public or sidekick. Some POST requests replace that entire object, so read it first and send back everything you want to keep.

Two changes are risky on production sites. Changing the code location can affect distributed caching. Changing the content location creates a new Content Bus ID, so all content must be previewed and published again, and indexes and sitemaps recreated. Instead, build a new site, validate it, then switch the CDN origin.

Legacy to config service

Older projects keep settings in files and sheets. Features such as repoless need the Configuration Service.

Older projects use fstab.yaml, .helix/config.xlsx, robots.txt, tools/sidekick/config.json, helix-query.yaml and helix-sitemap.yaml. The service combines these for compatibility, but some features are unavailable in this document mode. Adobe’s deprecations page lists file-based configuration as no longer supported, so move these sites.

Once enabled, settings in the Configuration Service override the old files, so remove the files afterwards to avoid confusion.

API keys and tokens

EDS has several credentials that look alike, and mixing them up can expose a site.

A sign-in token belongs to one user. It is highly sensitive and short-lived. An Admin API key is for automation, with listed roles and an expiry date. A site token gives read access to a protected site and is the one you give your CDN.

Create keys at the organization, profile or site level. You need the admin role. The key value appears once and Adobe does not store it, so put it in a secret manager immediately. Keys expire, so plan rotation before that date.

Profiles and repoless config

Fifty sites with fifty copies of the same header rule will drift. Profiles keep them aligned.

A profile groups reusable configuration, such as headers, indexes and additional metadata. Several sites in an organization can use one profile, but each site can use only one profile. If a site and its profile conflict, the site wins.

Repoless uses configuration to point several sites at one code repository. A canonical site must still match the GitHub owner and repository. A code merge reaches every site, so a profile change and a code change both have a wide reach.

Put inExamples

Hands-on lab: add a security header through configuration

Goal

Change one setting safely, and verify it.

You need

Admin access to a test site.

Time

About 45 minutes

  1. Read the current site configuration, and save a copy.
  2. Add a harmless test header on one path.
  3. Check the header with curl -I.
  4. Create an API key with the smallest role that does the job.
  5. Repeat a read with that key.
  6. Restore the original configuration.
  7. Delete the key.

Expected result

A verified change and a clean rollback.

How to verify

The header appears, then is gone after restore.

Stretch

Move the header into a profile and attach it to a second site.

  • Copy saved
  • Header verified
  • Minimal key used
  • Key deleted

Enterprise lens

Treat configuration like code. Script changes, keep a reviewed copy, and record who may run them.

Anything in the public configuration can be read at /config.json.

If admins use a custom tool for configuration, it must be usable by keyboard and screen reader.

Avoid fetching /config.json before the largest content appears.
