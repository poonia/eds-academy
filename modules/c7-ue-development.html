Component definitions

If it is not defined, authors cannot add it. Definitions are the Universal Editor’s catalogue.

component-definition.json lists what can be added. Each entry has a title, an id and an xwalk plugin section with a resource type and template.

A block normally uses core/franklin/components/block/v1/block. Its template sets name, shown as the block name, and model, which links to its fields.

The two required values

Every block must use the resource type core/franklin/components/block/v1/block and must set a block name. If either is missing, the block does not render. The model and filter are optional. Values placed in the template become the default content when an author adds the block.

aem.live is clear that you must not build custom AEM components for this. The markup these components produce is the stable contract between AEM and Edge Delivery.

Models and field types

The model is the author’s form. Field names also decide the block’s HTML.

A model has an id and fields. Common component types include text, richtext, reference, select, boolean and number. Check the current field list for the full set.

Field collapse combines properties by suffix: Title, Type, MimeType, Alt and Text. So imageAlt becomes the alt of image, and headingType sets the level of heading. Element grouping uses an underscore, so teaserText_title goes into the teaserText cell.

Filters

Filters keep pages consistent by limiting what goes where.

A filter has an id and a list of components. Container definitions refer to a filter by id. Add a block to the section filter to make it addable to sections.

Keep the lists tight. A smaller Add menu is easier for authors and easier to govern.

SymptomCauseFix
Block not addableFilter is missing itAdd its id.

Per-block model files

One huge JSON file makes every pull request a merge conflict. Per-block files avoid that.

In the xwalk boilerplate, each block has blocks/hero/_hero.json with its own definitions, models and optional filters. Shared items live under models/.

npm run build:json uses merge-json-cli to create the three root files, and a Husky hook runs it on commit. The root files are generated, so never edit them by hand.

Container blocks

Cards hold many cards. Container blocks model that.

A container block has its own properties and children. In the markup, its properties come first as single-column rows. Then each child is a row, with each of its properties as a column.

The container’s template sets a filter that allows its child type. A child uses the resource type core/franklin/components/block/v1/block/item.

SymptomCauseFix
Cannot add a childNo filter on the containerSet template.filter.

Instrumentation

The editor needs to know which element belongs to which content. Lose that link, and in-place editing breaks.

The Universal Editor uses data-aue-* attributes on elements, and semantic element attributes in the boilerplate’s helpers. When your decorate moves content into new elements, those attributes must move as well.

The xwalk boilerplate provides moveInstrumentation(from, to) in scripts.js for this reason.

UE extensions

Sometimes authors need a custom picker or a data lookup in the editor.

The Universal Editor can be extended through Adobe’s extensibility model, commonly using App Builder. Examples include custom field types and side panels.

Treat an extension as a product: it has authentication, hosting and upgrade costs. First see whether a model field type, a filter or a Sidekick plugin solves the problem.

Extension APIs change. Check Experience League for the current extension points before you plan one.

Type inference, field collapse and grouping

Authors fill in forms, but blocks need meaningful HTML. These three mechanisms turn separate fields into semantic markup, with no code of yours.

Type inference works from the value. An AEM asset with an image MIME type becomes a picture. Another reference, or a value starting with http, https or #, becomes a link. A value starting with a paragraph, list or heading is rich text. A multi-value property becomes a comma-separated list. Anything else is plain text.

Field collapse merges fields by name. A property ending in Title, Type, MimeType, Alt or Text becomes an attribute of its base property, not a value of its own. These suffixes are case sensitive. So image plus imageAlt becomes one picture with alt text. link, linkText, linkTitle and linkType become one link, and heading plus headingType becomes one heading.

Element grouping puts several elements into a single cell. A group name and an underscore go at the start of each field. A teaser could allow only a title, a description and up to two buttons, all in one cell, as if an author had written them in a document. That limits what authors can create while keeping the markup clean.

Block options and key-value blocks

Not every block is a list of content. Styles and settings have their own patterns, which keep you from building fields you do not need.

A field named classes is treated as block options, the same thing as a variant in a document. It appears in the block header for simple blocks, or as a value list for items in a container. Use a select or multiselect, so authors choose from valid options. You can split options across controls with element grouping, as in classes_size and classes_theme.

Setting key-value to true renders the block as name and value rows, which is what readBlockConfig expects. It suits settings-style blocks such as a feed of articles. Section Metadata works this way too.

The Columns block is special. It defines layout, not a content model, and it can only have rows, columns and classes properties. Its cells accept default content only.

Renaming a field later is costly, because the old name is stored in every existing component. Plan a content migration, or keep reading both names until migration is done.

Building a block end to end

Teams that write the code first often have to rewrite it when real content arrives. Adobe suggests working in a particular order.

Adobe recommends three phases. First, create the definition and model, review them, and take them to production. Next, create content with the block, so real markup exists. Last, write the decoration and styles against that real content.

That order means your JavaScript sees the exact markup authors will produce. In the Universal Editor you can see it working as soon as the definition is live, even with no styling. A simple block needs no JavaScript at all to be editable.

On a real project, work on a branch. The Universal Editor can load your branch by using the ref query parameter on the page URL. Merge once it has been reviewed.

Hands-on lab: build a Universal Editor block

Goal

Add a quote block that authors can edit in place.

You need

An AEM sandbox with the xwalk template, or a code walkthrough.

Time

About 2 hours

  1. Create blocks/quote/_quote.json.
  2. Define the definition and model.
  3. Add it to the section filter.
  4. Run npm run build:json.
  5. Push to a branch.
  6. Add the block in the editor and fill in its fields.
  7. Decorate it in quote.js with instrumentation intact.
  8. Confirm in-place editing still works.

Expected result

A working block in the editor.

How to verify

You can select and edit each part in place, and the live page is correct.

Stretch

Turn it into a container with several quotes.

  • Model created
  • Filter updated
  • JSON built
  • Editing still works
